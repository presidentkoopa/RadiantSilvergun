LAW -- SCORE IS ITS OWN CURRENCY (owner correction, recorded as law)
  Score does NOT convert to, feed, or draw from Gold Bits or any other
  economy. An earlier draft built a points-to-gold exchange rate; the
  owner rejected it outright. It is fully removed.
  The reasoning, kept so it is not re-derived: promotion owns permanent
  growth, Gun Bonsai owns weapon growth, Gold owns card rerolls, and
  score owns CONSUMABLES -- extra lives and ammo regen, nothing else. If
  a score cash-in is ever wanted it gets its OWN price list. It never
  becomes an exchange rate. Gold is awarded one at a time and score
  arrives in the hundreds; the two are not commensurable, and pretending
  otherwise either floods gold or makes score meaningless.

WHAT IT ACTUALLY DOES
  Base points per kill, then independent situational multipliers that
  stack, each announcing itself on the HUD as it pays. Fifteen bonuses:
    Efficiency  Spree, Untouchable, Infighter
    Style       Ambidextrous, Scrapping, Telefrag, Blindside, Darwin,
                Airborne
    Daring      Redline, Swan Song, Point-Blank, Brawler, Giant Slayer
  Three are NOT straight ports and are worth knowing:
    * AMBIDEXTROUS is dakka's Switcharoo re-aimed at this chassis. The
      original paid for firing 2+ weapons (or 2+ fire modes) in a short
      window; on a dual-wield mod that condition IS mainhand-then-
      offhand, so it became the signature bonus. Tracked by sampling
      button state in WorldTick -- NO weapon file was touched. dakka
      needed an ACS call in every fire state of every weapon; we do not,
      which also means it works on weapons we did not write.
    * SCRAPPING was "killed with the Scrapper", dakka's slot-1 junk gun
      (actually a dual-wielded pair that alternates hands -- its gimmick
      is already our chassis). The transferable idea is "you did it with
      bad equipment", and this project already ranks equipment, so it is
      now any weapon at VRT_Basic or below.
    * GIANT SLAYER is ours, not dakka's. It keys off the monster tier
      ladder, which is this project's real difficulty statement.

  TIER DRIVES VALUE. dakka scored base points off SpawnHealth. We use
  RS_MonsterMaster.TierMaxHealth inflated by Tier (rs_score_tierweight,
  default 0.12 -> a TEX is worth ~2.5x its HP). Non-RS monsters fall
  back to SpawnHealth, so it still works on a plain or foreign bestiary.

  THE REWARD BAR IS CALIBRATED PER MAP from that map's own monster
  population, so one bar means the same amount of work on MAP01 and on
  a slaughtermap. That is dakka's best idea and it was kept intact.

  IT HONORS THE KILL-REWARDS PAYOUT GATE. Summoned minions and transient
  boss stages score NOTHING -- the same rule RS_Bits already enforces,
  for the same reason: the Pain Elemental's escort is designed to
  respawn forever, so without this it is an infinite score farm. If
  score and Bits ever disagree about what a kill is, one of them is bugged.

  EXTRA LIVES use dakka's buddha trick: while a life is banked the
  player is in CF_BUDDHA, so lethal damage parks them at 1hp instead of
  killing them, and catching that 1hp state is the revive. Resurrecting
  an already-dead pawn loses weapon state and looks wrong.

  THE REVIVAL FIRE CONE (the owner's "death fire cone thing") is a port
  of DakkaReviveExplosion: opening blast, then eight flame streams and
  eight ground rakes thrown from an emitter spinning 2.5 deg/tic for ~70
  tics. Uses RSI1/RSI2 from sprites/combatfx/fire/ -- the sheets
  RS_FireLoop already draws from, verified present on disk (13 and 10
  frames). NO new art dependency; it cannot break from a missing asset.

CONTROLS
  ~70 cvars appended to CVARINFO.txt -- every bonus has its own on/off
  and its own magnitude, plus reward mode, regen shape, the whole cone
  (arms/duration/blast; blast 0 = cosmetic only), and a full HUD block
  (position as screen %, scale, per-element toggles, color presets).
  MENUDEF.txt: "Arcade Score" under Radiant Silvergun Options, with
  three subpages (Style Bonuses / Rewards & Extra Lives / Score Display).

PLACE, AND THE DIFFERENCE MATTERS.
  (Revised after syncing with the shotgunner/lint lane, which held the
  only compile log anyone has. The paragraph this replaces said flatly
  that none of it had ever compiled; that is too strong for the core.)

  RS_Score.zs -- PARSES CLEAN, FULL COMPILE UNCONFIRMED.
    The compile log behind 6f032dca is silent on RS_Score.zs: no error,
    no warning, no deprecation. Every entry in it is under
    zscript/monsters/**, across 26 files.
    The ORDERING is what makes that meaningful rather than merely
    absent: at 6f032dca, zscript.txt line 8 is RS_Score.zs, the first
    monster include is line 39, and the projectile files that actually
    produced errors start at line 52. The compiler reached RS_Score.zs
    31 lines before anything that spoke, and said nothing about it.
    TWO CAVEATS, kept deliberately -- "it compiles" is exactly the kind
    of claim that has cost sessions here:
      1. That log is the owner's paste. It can be shown silent on
         RS_Score; it cannot be shown unfiltered or complete.
      2. The build had hard errors in it. Passing early parse and
         property resolution is NOT surviving codegen and virtual
         resolution, which may not have run to completion for any file.
    So the honest claim is "parses and resolves its properties", not
    "compiles". Still the first positive signal this file has had.

  RS_ScoreHUD.zs and RS_ScoreRevival.zs -- GENUINELY NEVER COMPILED.
    Independently confirmed from the other side: at 6f032dca, line 8 is
    the ONLY RS_Score entry in zscript.txt. Their includes arrived in
    9b3d733b, after that build. These two are where first-boot breakage
    should be expected, and they revert by deleting two include lines
    without touching the core.

  What was done instead of a test-load is a static review, which caught
  four real errors:
    * `invoker.` used in plain Actor states (RS_ScoreRevival) -- invoker
      is only meaningful where an item's states run on its owner.
    * a field named `players` shadowing the engine's global players[],
      which silently breaks every players[i].mo lookup in the class.
    * cvar helpers callable from both play and ui needed `clearscope`;
      plain `static` defaults to the class's play scope, making the ui
      callers a compile error.
    * the HUD field needed `ui` (GunBonsai's handler declares its own
      the same way, EventHandler.zsc:12) -- RenderOverlay assigns it
      from ui scope, and a play field cannot be written from ui.
  python dedupe_check.py passes (no case-insensitive collisions).
  "Statically reviewed" is NOT "compiles". Expect a first-boot punch
  list. The revert path is clean and unchanged: drop the includes and
  the MAPINFO registration and the rest of the mod is untouched -- this
  system adds files and appends to config lumps, it restructures nothing.

     one ("we could even cash in the points somehow", "we would need to
     figure out score costs for things") and it was never resolved.
     What IS settled is the LAW, recorded above: never gold, never an
     exchange rate, its own price list if it exists at all.
     What is NOT settled: whether a spend should exist, and on what.
     The granularity problem is the reason it stalled and it is real --
     gold is awarded one at a time, score arrives in the hundreds per
     kill, so any price list has to be authored in score's own units
     rather than translated from an existing one. Do not start building
     a shop before this is answered; the answer determines whether the
     reward thresholds need re-pacing too.

  4. REWARD PACING, ONLY ANSWERABLE BY PLAYING IT. The per-map bar is

     and sound, but the constants are untuned for THIS bestiary and this
     project's tier-weighted point values. A bar might land every 30
     seconds or once per map. One real playthrough settles it; no amount
     of reading the code will.
