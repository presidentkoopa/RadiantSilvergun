--Promotion system (docs/rs_01_promotion_system.txt has the full spec -- this is the summary)

Real, implemented, in RS_Weapon.Promote():
  - Gate: only from Tier == Prototype.
  - Proportional 20% cut on all five rolled stats (DamagePerShot/Accuracy/Velocity/CritChance/
    Capacity) -- 20% OF the current value, not a fresh re-roll, not a flat subtraction.
  - Tier -> Basic, GunBonaiSockets -> RS_Roll.SocketsForTier(Basic) (0), read fresh not hardcoded.
  - PelletCount +1 (flat, every weapon type today -- shotgun-family probably wants a smaller
    number here per the Cyberdemon-math finding below; not decided, not built).
  - PromotionCount +1, permanent, never resets.
  - RollPromotionCurse() -- escalating: Nth promotion rolls N independent curse chances (was a
    flat repeating chance, changed after you called it "too much" and I misread the fix once).
    A hit locks a random stat at 50% of its cut value, tags the weapon "curse:<statname>".
  - UnlockStat() -- lifting ANY lock (Cursed-tier original or a Promotion curse, same flags,
    same function) gives a real 1.5x boost on top of whatever the stat was at while locked.
  - GetDamageCeiling() -- data-only stub, 1.8x placeholder off PromotionDamageBaseline. Nothing
    calls it yet -- there's no RS-side (or GunBonsai-side) level-up stat picker to plug it into.
  - All 32 duplicate per-weapon ApplyUpgradeCard overrides (main arsenal + GH set) deleted; the
    base class now does this correctly in one place. Bonus find: RS_RocketLauncher's old override
    was silently missing the pellet bonus entirely -- fixed as a side effect.

STUBBED OFF ON PURPOSE (short-circuited, not deleted -- same disable idiom as RS_Roll's earlier
Condition-effects stub):
  - RollPromotionCurse() -- the whole curse mechanism. `if (true) return;` at the top.
  - Curse Bit kill-reward roll in RS_Bits.zs -- `false &&` short-circuit.
  Flip both back on with a one-word edit whenever curses are wanted again.

Reference math, not RS's real data: the "3 promotions = boss-viable" conclusion in
rs_01_promotion_system.txt was sanity-checked against an EXTERNAL Colourful-Hell-style monster
tier file (HF_Monster/HF_Zombieman/HF_Cyberdemon, shown as examples only) -- not RS's own monster
tiers, which don't exist yet. Re-check that conclusion once real monster tier numbers exist.

--Curse Bits / Grey Bits (RS_Bits.zs)

Built as stacking currency pickups (accumulate in inventory, no auto-effect -- same shape as
ammo, not like the instant-effect Health/Armor/Ammo bits). Both reuse the Health Bit's gem sprite
recolored via STYLE_Shaded + SetShade (rust red for Curse, silvery grey for Grey/repair) instead
of new art. Grey joins the normal weighted kill-reward pool (rs_bits_ratio_grey). Curse is
deliberately rarer and OUTSIDE the pool -- its own independent per-kill roll, rs_bits_curse_chance.
Currently stubbed off along with the curse mechanic (see above).

NOT BUILT: the actual "spend X Curse/Grey Bits" menu action. RS_Weapon.RepairWithGreyBits() and
UnlockStat() both already do the real work once called -- nothing calls them from a menu yet.

--GunBonsai graft (RS_GunBonsaiBridge.zs -- the one file allowed to reference both RS_Weapon and
vendored TFLV_* types)

  - OnWeaponPromoted() -- strips every GunBonsai-granted affix when a weapon promotes (drops to
    0 sockets). OnDeactivate() runs first so persistent side effects get reversed properly.
  - NotifyFired() -- the offhand-attribution fix described above.
  - XP-curve discount -- COULDN'T be a pure extend-class graft (GetXPForLevel() is a concrete
    method called internally by TFLV_WeaponInfo's own code, extend can only ADD members, not
    replace a method body). Small guarded edit directly inside zscript/GunBonsai/WeaponInfo.zsc
    instead -- 15% off per PromotionCount, capped at 60% off. Consistent with this project's
    existing precedent (the offhand/GBOH additions already edit vendored files, not pure-graft).

Full audit of GunBonsai's own offhand-related code confirmed WorldThingDamaged is the ONLY real
hand-detection logic anywhere in it -- everything else (HUD, status menus, WorldTick caching)
just reads player.OffhandWeapon directly or reads data WorldThingDamaged already populated. The
fix above is complete, not "probably complete."

Also examined (not changed, just confirmed): BONSAIRC still has zero stanza for any RS/VR weapon
class (wildcards like `type VR_Revolver*: PROJECTILE;` are supported whenever wanted -- cheap,
just not done). GunBonsai's stock ~50-60 upgrades are still ALL registered and offered to
players -- the stated plan to dump most of them and author new per-family/per-tier ones hasn't
started. Confirmed there is NO Tier/Socket gating axis anywhere in GunBonsai natively
(TFLV_Upgrade_BaseUpgrade.IsSuitableForWeapon() defaults false, every stock upgrade overrides it
individually with its own logic -- no hook for "is this weapon's tier high enough" exists to plug
into, it would need to be built from scratch).

--Real compile/runtime bugs found and fixed

  - `static const string X[] = {...}` array-literal syntax does not resolve reliably on this
    engine build. Found and fixed THREE times: RS_Keywords.zs (KnownKeys), RS_Bits.zs (blacklist),
    and zscript/GunBonsai/settings.zsc (levelup_sound's sounds[] array) -- the last one is almost
    certainly the actual, literal reason the GunBonsai level-up sound never played. All three
    rewritten to plain comparison chains / switch statements. If you ever see "Unknown identifier"
    pointing at something that looks like a real declared symbol, check for this pattern first.
  - RS_GunBonsaiBridge crashed on load: `extend class PlayerPawn` -- "class playerpawn cannot be
    found in current translation unit" on this engine build. Fixed by extending VR_DualClassBase
    (RS's own player class) instead of the raw engine PlayerPawn.

RS_Catalog.zs) + Profile (RS_AttackProfile, the assembly unit holding multipliers + catalog
references). A_RS_FireSlot is where all four meet every shot. Use this name going forward instead
of re-explaining the four pieces each time.

  - RS_AttackProfile gained a Trail field (matching ImpactPuff/ImpactSparks/MuzzleSmoke), wired
    through MakeBullet()/Clone()/SetupFeedback(). RS_Catalog gained TRAIL_Ballistic().
  - RS_BallisticTrail (renamed from an initial "RS_BallisticTrailBit" -- deliberately avoids
    "Bit," which already means the kill-reward currency classes) replaces the old RS_BallisticGhost
    as the in-flight glow effect -- additive render, adopted directly from a TrueBullet reference
    file you shared (TB_TrailBit), reskinned onto the existing RSB0 sprite instead of new art.
  - RS_BallisticFired's Death: state rewired: used to be a bare hardcoded sprite frame with NO
    spark at all on the default path. Now spawns RS_Catalog.PUFF_Bullet() + SPARK_Hit() by
    default, still overridable per-profile.

--Weapon Sound Assignment (new menu system)

Options -> Radiant Silvergun Options -> Weapon Sound Assignment. One row per main-arsenal
archetype (not per numbered weapon variant -- they already share one BuildAttackProfiles(), so
one choice covers all 6). RS_Weapon.GetEffectiveFireSound() derives the cvar key straight from
the weapon's own archetype: keyword -- no per-weapon-file overrides needed or wanted (this was
corrected mid-build after over-engineering it as per-file virtuals the first time). Dispatch
lives in one place, RS_Catalog.ResolveArchetypeSound(). Only Revolver has real alternates today
(3 new SNDINFO entries, files that already existed on disk unregistered); every other archetype
shows "Default" alone and is ready for more takes whenever sourced. Cvar names match the REAL
archetype keyword value, not the obvious class-name guess -- Chainsaw is archetype:melee (cvar:
rs_soundchoice_melee), Rocket Launcher is archetype:launcher, Plasma Rifle is archetype:energy,
BFG9000 is archetype:bfg. This was a real bug caught and fixed before it shipped.
