================================================================================
 PART 0 -- THE COMPETITION, AND THE ONE THING THEY CANNOT DO
================================================================================

GearBox (mmaulwurff) -- the polished incumbent. Three representations
(blocks / wheel / plain text), mouse input for wheel mode, multiplayer-safe,
can drop items from the menu, reads `Inventory.AltHudIcon` to support modded
weapons. Requires GZDoom 4.5+. Now folded into mmaulwurff/doom-toolbox.

PyWeaponWheel (DrPyspy) -- reflection-driven. Walks AllActorClasses at runtime,
so it works against mods it's never heard of. Hand-rolled tokenizer for a
PYWHEEL config lump (exclude/include/merge/forceicon/rename/hide/renderstyle/
alpha). Freezes the world while open and manually preserves psprite + powerup
tics across the freeze.

THE GAP: GearBox's author has publicly stated they would need outside help to
support VR, because they do not own VR hardware. Both mods drive selection from
2D mouse-delta input -- that input model IS their architecture, not a detail
layered on top. Neither can be ported to VR-native without a rewrite.

RS_Main has: the engine source (E:\DXR2), exact position AND orientation per
hand, and a codebase already built around two genuinely independent hands.
That is not an incremental advantage. It is a different category of product.

COROLLARY: do not compete on wheel-ness. A wheel is what you build when 2D
mouse input is all you have. Competing there means adopting their constraint.


================================================================================
 PART 1 -- THE REFRAME: TWO SETS, TWO DIFFERENT PROBLEMS
================================================================================

This is the central finding. There is not one selection problem here. There are
two, and they want opposite solutions.

-------------------------------------------------------------------------------
 1A. VANILLA+ = A NAVIGATION PROBLEM. This is the wheel case.
-------------------------------------------------------------------------------

RS_VP_* is a classic Doom arsenal wearing better models:

  - 10 visually distinct weapons. Fist, Chainsaw, Pistol, ARifle, Shotgun,
    SuperShotgun, Chaingun, RocketLauncher, PlasmaRifle, BFG9000.
  - Classic slot layout: 1 (Fist/Chainsaw), 2 (Pistol/ARifle), 3 (Shotgun/SSG),
    4 (Chaingun), 5 (RL), 6 (Plasma), 7 (BFG).
  - Only 2 identities each -- mainhand + a "2"-suffixed offhand sibling.
  - `Condition` is hardcoded to 100.0 on all ten. There is no per-instance
    state worth comparing.
  - 8 of 10 mainhands carry `replaces <Vanilla>`, so they appear on real maps.
  - 9 of 10 already have working voxel pickups on disk (see 3E).

Nothing to inspect. You need to get to the shotgun, fast, without thinking.
A selector earns its keep here, and this is the head-to-head-with-GearBox case.

-------------------------------------------------------------------------------
 1B. MAIN ARSENAL = A COMPARISON PROBLEM. A wheel is useless here.
-------------------------------------------------------------------------------

rs_00_overview.txt:41-49 -- independent left/right inventories; each class holds
exactly six class weapons, three mainhand and three offhand.

rs_00_overview.txt:47, the author's own words:
  "The goal is not to recreate a traditional Doom weapon wheel with dozens of
   weapons."
and :49:
  "(My thinking is that handling a whole Doom arsenal in each hand is unwieldy.
   A smaller number of player-specialized weapons is a better move.)"

The problem is not that three is too few to need a wheel. The problem is that
the three are NEAR-IDENTICAL. A Dual Revolvers player accumulates up to three
rolled revolvers per hand across slots 2/3/4. All six identities of a weapon
type share:

  - the same Spawn sprite and the same Ready sprite,
  - the same States block (subclasses override ONLY Tag / SelectionOrder /
    SlotNumber / AmmoType2, plus the offhand flag),
  - the same MODELDEF geometry and transforms (all 61 blocks are byte-identical
    duplicates; only the skin string differs, and in practice only the Pistol's
    skin actually varies -- WPN-9mm.png vs WPN-9mm2.png).

They differ only in invisible rolled numbers and a name:
  VR_Revolver  "Moonlight Magnum"   VR_Revolver4 "Crimson Vow"
  VR_Revolver2 "Sunset Cannon"      VR_Revolver5 "Widow's Chime"
  VR_Revolver3 "Ashwood Sentinel"   VR_Revolver6 "Iron Requiem"

Cycling blind through three things you cannot tell apart is the actual failure
mode. The need is COMPARISON, not navigation. See Part 5.

 1C. THE SWITCH ALREADY EXISTS IN THE KEYWORD DRAFT
-------------------------------------------------------------------------------

rs_01_weaponkeywords_v01.txt has `set: silvergun | vanillaplus`. The draft

================================================================================
 PART 2 -- THE BLOCKER: THERE IS NO WAY TO PUT A WEAPON IN A HAND
================================================================================

Nothing in Parts 4 or 5 can be built until this is fixed. It is the real gate
and it is not a UI problem.

THE CURRENT STATE:

`player.OffhandWeapon` is written in exactly three places, ALL at acquisition
time, all last-write-wins with no arbitration:

  zscript/weapons/RS_Weapon.zs:368-369
      override void AttachToOwner(Actor newOwner)
      ... if (bOffhandWeapon && newOwner.player)
              newOwner.player.OffhandWeapon = self;
      (comment :363-364 defers mainhand placement to the engine's own default
       ReadyWeapon assignment)

  zscript/weapons/rs_weapon/RS_Fist.zs:22-27
      VR_Fist2.AttachToOwner -- sets it UNCONDITIONALLY (no bOffhandWeapon
      gate), because VR_Fist2 descends from vanilla Fist, not RS_Weapon.

  zscript/weapons/RS_VP_Weapon.zs:51-68
      TryPickup morph -- spawns the offhand class at Pos, calls its TryPickup,
      Destroy()s the original.

`AttachToOwner` fires ONCE, at acquisition. It never fires again for a weapon
already in inventory. Therefore: THERE IS NO RE-SEAT PATH. You cannot move an
owned weapon into a hand. That primitive does not exist.

Compounding it: `+WEAPON.NOHANDSWITCH` is set on every class in both sets and
is NEVER negated -- including on the offhand identities 4/5/6. Engine-side hand
switching is deliberately off, project-wide.

THE PREVIOUS ATTEMPT, AND WHY IT MATTERS:

zscript/systems/RS_OffhandSeat.zs exists but is disabled at zscript.txt:5:
    //#include "zscript/systems/RS_OffhandSeat.zs"  // disabled -- see plan
    //   history, offhand system needs rebuilding

Git shows the file and the commented include arrived together in 33d252a -- it
has never been compiled on the current tree. There is no "worked then broke"
commit, and the concrete reason is not recorded anywhere in docs/.

Its seating logic was the right shape and should be the starting point
(RS_OffhandSeat.zs:74-91):

    if (offWep)  { offWep.bOffhandWeapon = true;   offWep.bNoHandSwitch = true;
                   pawn.player.OffhandWeapon = offWep; }
    if (mainWep) { mainWep.bOffhandWeapon = false; mainWep.bNoHandSwitch = true;
                   pawn.player.ReadyWeapon = mainWep; }
    pawn.player.PendingWeapon = WP_NOCHANGE;
    pawn.BringUpWeapon();

Its actual flaws: it was a one-shot boot-time scan (per-player `done[]` flag,
MAX_TRIES = 35 then give up forever, :16), so it could only seat at spawn and
never re-seat; and its `PendingWeapon = WP_NOCHANGE` + `BringUpWeapon()` fights
VR_DualClassBase.PostBeginPlay's force-equip (VR_PlayerClasses.zs:59, which
sets `player.PendingWeapon = w` precisely because engine default selection was
"leaving the player holding fists instead of their class weapon", :36-37).

WHAT NEEDS TO EXIST:

An authoritative per-player hand registry that owns which weapon is in which
hand and can change it at any time -- not only at pickup. Requirements:

  R1. Re-seat an already-owned weapon into either hand, on demand.
  R2. Arbitrate against the three acquisition-time writers above, so a floor
      pickup cannot silently clobber a deliberate choice. (Today
      AttachToOwner:368 unconditionally overwrites OffhandWeapon on ANY
      offhand-flagged pickup.)
  R3. Coexist with VR_DualClassBase.PostBeginPlay's force-equip rather than
      race it.
  R4. Survive the VP TryPickup morph, which Destroy()s an actor mid-pickup --
      any cached Weapon pointer goes dangling (RS_VP_Weapon.zs:63).
  R5. Not fight `+WEAPON.NOHANDSWITCH`. Since it is set everywhere and never
      negated, the registry must do its own seating, not delegate.

Suggested home: zscript/systems/, matching RS_Roll / RS_Bits / RS_DebugMenu.
Suggested shape: EventHandler + NetworkProcess netevent dispatch, which is the
established pattern in this project (see 3H).

NOTE ON SCOPE: this is worth building even if no selection UI is ever built. It
is a real, currently-missing capability, and rs_00_overview.txt:43-49 describes
per-hand independent inventories as a core design pillar.

-------------------------------------------------------------------------------
 3A. THERE ARE NO WEAPON ICONS. ANYWHERE.
-------------------------------------------------------------------------------

`Inventory.Icon` is set on ZERO classes across the entire project -- not one
weapon, not one ammo class, in either set. Repo-wide grep for "Icon" in
zscript/ returns no hits at all. The only two matches in the whole repo are
prose: docs/HANDOFF_3.md:375 ("icons that never got made") and
docs/rs_01_weaponkeywords_v01.txt:312 (an unrelated "icon-scale" keyword).

Consequence: a conventional 2D icon grid/wheel has NO ART TO DRAW. It would
need either ~20 hand-made icons, or PyWeaponWheel's sprite-frame-scraping
fallback. This inverts the usual cost assumption -- see 3B and 3E, where 3D
assets DO already exist and are already audited.

Note this also means GearBox's modded-weapon integration path
(`Inventory.AltHudIcon`) is unavailable to us for free.

-------------------------------------------------------------------------------
 3B. MODELS: WHAT EXISTS, AND THE BINDING TRAP
-------------------------------------------------------------------------------

MODELDEF is a single 2823-line root-level lump, no extension. There are NO
`.modeldef` files on disk (every docs/models/ header claiming "Sources:" is
stale on this point). 292 Model blocks, 146 Skin/Scale/Path, 90 Offset.

  - ALL 61 main-arsenal weapon classes have models, plus vanilla `Fist` and
    `VR_Fist2`.
  - THE ENTIRE Vanilla+ SET HAS ZERO MODELDEF ENTRIES. Sprite-only, with voxel
    world pickups instead (3E).

THE BINDING TRAP: MODELDEF binds `Model <ActorClassName>` plus
`FrameIndex <SPRITE> <letter> <submodel> <frame>`. The CLASS gates it; the
sprite+frame selects which model frame shows. So a display object only renders
a model if its own class has a MODELDEF block AND it plays a matching sprite.
There is no per-instance model assignment in the data layer.

  -> `A_ChangeModel` / `SetAnimation` / `ModelData` appear NOWHERE in zscript/.
     zscript.txt declares `version "4.14"`, so A_ChangeModel should be
     available (GZDoom 4.11+). If it works in DXR2, ONE generic dummy actor
     class can wear ANY weapon's mesh on demand, and no new MODELDEF blocks are
     needed at all. THIS IS THE SINGLE LOAD-BEARING UNVERIFIED ASSUMPTION IN
     THIS DOCUMENT. Verify before designing around it. (Fallbacks in 3E/3F.)

ALREADY TRUE TODAY: four main-arsenal Spawn-state pickup sprites are already
MODELDEF-bound, so those floor pickups render 3D models in world space right
now -- VR_Chaingun (CHGG A), VR_Revolver (REVO A), VR_Rifle (RIFK A),
VR_Shotgun (SHTG A). Pistol (PSP1), SMG (SMP1), SSG (SGN2), RL (RLP1),
Plasma (PLP1), BFG (BFP1) are unbound and stay flat sprites.

THREE PROBLEMS:

  (1) ~6:1 SIZE SPREAD. Pistol is 23 units long, RocketLauncher 151. A uniform
      floating arrangement needs per-weapon normalization to a target
      longest-axis.

  (2) ORIGIN IS THE GRIP, NOT THE VISUAL CENTER. Every MD3 has localOrigin
      0,0,0 except pistolet/rev/m16/shotgun/ssg/minigun. For a floating display
      you must translate by -(bbox center x scale). Worst offenders: Revolver
      (center Z -38.7, because frame 0's bbox spans the whole animation
      envelope), Chaingun (+71.6 X), BFG (+55.5 X).

  (3) TWO INCOMPATIBLE SCALE CONVENTIONS COEXIST. `1.35 1.35 1.35` (54 uses,
      unmirrored upscale) vs `-1.0 1.0 1.0` (44 uses, X-MIRRORED -- the
      established VR hand-attachment mirroring convention, documented at
      MODELDEF:2793). A display actor must reproduce the sign or the mesh
      renders reversed.

  => A per-weapon normalization table is required. Bounded work, but it is real
     data entry, ~11 rows. Do not hand-wave it.

NOT AVAILABLE: no `USEACTORPITCH`, `USEACTORROLL`, `INHERITACTORPITCH`,
`Rotation`, `AngleOffset`, `RollOffset`, or `DONTCULLBACKFACES` anywhere. Only
`PitchOffset` (SMG only: 45.0 on the reload block, 0.0 on ready) and
`ZOffset -5` (SMG only).

MUZZLE-FLASH SUBMODELS ARE USELESS AS DISPLAY MESHES -- revf/pistF/shotgunF/
ssgF/m16f/minigunF are degenerate, zero-size bboxes (a single flat quad).

UNREFERENCED BUT PRESENT, AND POSSIBLY BETTER SUITED: five world-view pickup
models exist on disk and are bound to nothing --
  W-BFG.md3, W-Chaingun.md3, W-Chainsaw.md3, W-PlasmaRifle.md3,
  W-RocketLauncher.md3
They are compact (~53-62 units), origin 0,0,0, and already authored as world
objects rather than first-person meshes -- i.e. exactly what a floating display
wants. But there are only five; no W- model exists for revolver, pistol, SMG,
rifle, shotgun, or SSG. Also unreferenced: minigun.md3, minigunF.md3,
CG_MF1/2.md3, chainsaw.md3+png, SnipaRPG.md3+Snipa.png, m16f.md3,
WPN-REV2.png, WPN-9mm3/4/5/6.png, mf0-3.png, flash2.png, five G*.pcx palette
files, and a stray "guns - Shortcut.lnk". A VR_Chainsaw model folder exists
with no class and no MODELDEF entry.

-------------------------------------------------------------------------------
 3D. LIVE RUNTIME MODEL TWEAKS DO WORK
-------------------------------------------------------------------------------

zscript/systems/RS_DebugMenu.zs:335-346 (ToggleHeldMirror) does
`w.Scale.X *= -1` on both held weapons from a netevent, described in-file as
"Purely cosmetic and not persisted -- resets on weapon switch/respawn."

Proves: an actor's Scale vector is live-writable at runtime from ZScript with
no MODELDEF edit and no reload. That is the hook for per-weapon normalization
(3C) and for a grow/shrink selection highlight.

-------------------------------------------------------------------------------
 3G. UI RENDERING: WHAT'S PROVEN, AND HOW MUCH IS GREENFIELD
-------------------------------------------------------------------------------

Only TWO drawing primitives are used anywhere in the project:
`Screen.DrawTexture` and `Screen.DrawText`. `DrawShape`, `DrawShapeFill`,
`DrawLine`, `DrawThickLine`, `DrawChar`, `DrawTextureRotated`: ABSENT.

DTA_ flags actually in use: DTA_VirtualWidth, DTA_VirtualWidthF,
DTA_VirtualHeight, DTA_KeepRatio, DTA_DestWidth, DTA_DestHeight, DTA_Color,
DTA_Alpha, DTA_ClipLeft, DTA_ClipRight, DTA_LeftOffset, DTA_TopOffset.
ABSENT: DTA_Rotate, DTA_FlipX/Y, DTA_ScaleX/Y, DTA_ClipTop/Bottom,
DTA_Desaturate, DTA_LegacyRenderStyle, DTA_TranslationIndex.
Nothing non-axis-aligned is drawn anywhere in this project.

Nice technique worth stealing: the XP bar draws a full texture clipped to a
fraction, and picks the DTA_ tag itself at runtime by ternary --
GunBonsai/HUD.zsc:141-147, `(mirror & HUD_MIRROR_H) ? DTA_ClipLeft : DTA_ClipRight`.
Mirroring is done ARITHMETICALLY plus a pre-mirrored texture chosen by numeric
suffix (`tex(frame_tex..face)`, HUD.zsc:188-195), never by a flip flag.

WORLD-TO-SCREEN PROJECTION IS TOTAL GREENFIELD. `RenderOverlay(RenderEvent evt)`
is declared at GunBonsai/EventHandler.zsc:123 and **`evt` IS NEVER READ ONCE**.
No RenderEvent field is accessed anywhere in the project -- no camera, no
viewpos, no FracTic. Everything is pure 2D screen overlay in three tiers
(a fixed 1536x512 "HUD texture space", a virtual/framebuffer space, and real
screen space used only for clipping -- HUD.zsc:4-64, 126-140).
=> Drawing a 2D label anchored to a 3D world position is possible and has zero
   precedent here. It is new code, not a borrowed idiom.

ANALOG INPUT HAS ZERO PRECEDENT. `MenuEvent(int key, bool fromController)` is
the ONLY input handler in the project. `fromController` is accepted, forwarded
to super, and NEVER INSPECTED. `OnUIEvent`, `MouseEvent`, `OnInputEvent`,
cursor coordinates, analog axes: ABSENT. Everything is MKey_Left / MKey_Right /
MKey_Enter / MKey_Back (GenericMenu.zsc:119-133, 158-166).
=> VR pointing/grabbing input must be built from scratch. Nothing to copy.

ANIMATION: exactly one animated thing exists -- GetShinyColour(offset),
HUD.zsc:166-177, a hand-rolled triangle wave over `gametic` read directly in
UI scope, three channels phase-offset 0/34/68 tics. No fades, no easing, no
transitions, no sub-tic timing. `level.time`, `MSTime()`, `FracTic`: ABSENT
from UI code. Tic-granular `gametic` in ui scope is the only clock precedent.

SCOPE-CROSSING PATTERN, important: RenderOverlay is `ui` scope, so the offhand
HUD is fed by play-scope-written cache fields (`gboh_offhand_weapon`,
`_level`, `_xp`, `_maxxp` -- EventHandler.zsc:118-121) that ui then reads. It
stores a `Weapon` pointer readable from ui. Any new UI will need the same
bridge. => WHICH SCOPE THE PER-HAND CONTROLLER POSE IS READABLE FROM IS AN
OPEN QUESTION THAT DETERMINES THE WHOLE ARCHITECTURE. Resolve early.

MENU LIFECYCLE: opening is always play-scope `Menu.SetMenu(name)` guarded to
consoleplayer (UpgradeGiver.zsc:51, EventHandler.zsc:149). There is NO

 3H. ESTABLISHED PATTERNS TO REUSE (do not reinvent)
-------------------------------------------------------------------------------

MENU/KEY ACTION -> GAMEPLAY CODE. The one sanctioned route, used by the whole
debug menu. MENUDEF `Command "Label", "netevent <name>"` -> an EventHandler's
`override void NetworkProcess(ConsoleEvent e)`. Rationale is stated at
RS_DebugMenu.zs:4-8 (MENUDEF Command can only run console commands).
Dispatcher shape (RS_DebugMenu.zs:352-374) is a flat case-insensitive chain:
    let plr = players[e.Player];
    if (!plr || !plr.mo) return;
    if (e.Name ~== "rs_debug_vp_giveall") GiveAllVP(plr);
    else if (...)
16 netevents currently wired. Handlers are `static void Fn(PlayerInfo plr)`.

KEYBIND -> NETEVENT (KEYCONF, 21 lines):
    addmenukey "<label>" <alias>
    alias <alias> "netevent <name>[,<args>]"
    defaultbind <KEY> <alias>
ONLY TWO KEYS ARE TAKEN IN THE WHOLE PROJECT: I (gboh-unified-info) and
P (bonsai_cycle_ld_effect). No RS-owned keysection exists yet. The rest of the
keyboard is free.

PER-PLAYER UI STATE WITHOUT SUBCLASSING THE PAWN: `user`-scope cvars fetched
via `CVar.GetCVar(name, plr)` -- RS_DebugMenu.zs:84, :110, rationale at :17-18
("no need to touch any player pawn class to add state").

SPAWN TEMPORARY ACTORS WITH A LIFETIME: RS_Bits.zs is the model. Own `int`
counter + `override void Tick()` + `Destroy()`, duration from cvars via
`RS_BitUtil.TickLife(in out int)` (:15-27, and note total<=0 means never
expire -- which is the current default, so bits never expire today).
Placement via `a.A_SpawnItemEx(...)`; from a static non-Actor context use
`Actor.Spawn(...)` (RS_DebugMenu.zs:249-251).

WEAPON ENUMERATION IDIOM: `for (Inventory item = mo.inv; item != null;
item = item.inv) { let wep = Weapon(item); ... }` -- RS_Bits.zs:160ish
(RS_GiveAmmoBit). NOTE: RS_DebugMenu contains NO inventory iteration at all;
it uses two hardcoded name lists (VPWeaponList :32-44, DualWeaponList :56-65)
plus naming conventions (`VPOffhandName()` = name+"2" with an
`RS_VP_BFG9000` -> `RS_VP_BFG90002` special case, :46-51; dual offhand =
name+"4", :116). A UI that enumerates by inventory will DIVERGE from the debug
menu's view of the world. Pick one and be consistent.

COUNT/CAP WORLD INSTANCES: `ThinkerIterator.Create("ClassName")`
(RS_DebugMenu.zs:269-272, :317-318; RS_FX_HiFiFX.zs:103).

ZSCRIPT GOTCHAS ALREADY HIT AND DOCUMENTED IN-TREE:
  - A function cannot return a dynamic array by value; use `out Array<T>`
    (RS_DebugMenu.zs:30-31).
  - `EVR_Tier(intValue)` is not valid cast syntax; hence TierFromInt()
    (RS_DebugMenu.zs:142-155).
  - `Spawn(...)` has no implicit self in a static method on a non-Actor class;
    use `Actor.Spawn(...)`.
  - ZScript has no reify, hence libtooltipmenu's five-mixin duplication
    (Tooltips.zsc:166).

CVAR CONVENTION: `rs_<system>_<setting>`, lowercase snake_case. `server` for
anything gameplay/FX-affecting, `user` for per-player UI and debug state.
47 cvars currently: 5 rs_fx_*, 3 rs_vanillaplus_*, 1 rs_dualclass_*,
2 rs_debug_* (user), 16 rs_bits_*, 29 bonsai_* (kept under upstream's prefix
deliberately, CVARINFO.txt:43-45).

MENUDEF depth is currently 3. RS_MainOptions branches six ways: RS_FXSettings

-------------------------------------------------------------------------------
 3J. THINGS THAT WILL FIGHT A SELECTION SYSTEM
-------------------------------------------------------------------------------

  J1. NEVER SWITCH TO PREVIEW. Every weapon switch runs
      `infoForCurrentWeapon.OnDeactivate()` then `.OnActivate()`
      (PerPlayerStats.zsc:120-124) -- these are LIVE GAMEPLAY EFFECT TOGGLES
      (UpgradeBag.zsc:70-80, per-upgrade virtual calls). Scrubbing a highlight
      through weapons while actually switching would churn upgrade activation.
      Highlight must be display-only; commit exactly once.

  J2. SWITCH DETECTION IS POLL-ONLY. There is NO weapon-switch event in
      GunBonsai; it compares `infoForCurrentWeapon.wpn == wielded` every tic
      (PerPlayerStats.zsc:87). Reading `GetInfoForCurrentWeapon()` in the SAME
      tic as a programmatic switch returns null (documented :82-83).

  J3. MENU MUTEX. `stats.currentEffectGiver` (PerPlayerStats.zsc:46) is a
      global claim; a giver parks in `AwaitChoice` waiting for a pick. Do not
      open a UI while a level-up is pending.

  J4. VM ABORT RISK. `Fanfare()`/`StartLevelUp()` dereference `wpn.owner`
      unguarded (WeaponInfo.zsc:183, 186, 192, 215). Switching away from or
      dropping a weapon with a pending level-up can abort.

  J5. GUNBONSAI IS MAINHAND-CENTRIC UNDERNEATH. PerPlayerStats has zero
      offhand awareness -- GetInfoForCurrentWeapon (:86),
      CreateInfoForCurrentWeapon (:121), GetCurrentStats (:59-75), ModifyDamage
      (:368), and the OnProjectileCreated/OnDamageReceived/OnKill/OnPickup
      hooks (:317-357) all read only `player.ReadyWeapon`. `ShouldDrawHUD`
      requires a ReadyWeapon (:111), so the OFFHAND HUD VANISHES if no mainhand
      is equipped. A hand registry that can empty the mainhand will expose this.

  J6. NO SERIALIZABLE WEAPON ID EXISTS. Only actor pointers and class names.
      `bonsai-toggle-upgrade`/`bonsai-tune-upgrade` index into the CURRENT
      weapon's bag only. Inspecting/acting on an arbitrary weapon needs new
      netevents carrying some weapon identity -- which has to be invented,
      because class name is ambiguous across the six identities.

  J7. REASSIGNING A HAND RETARGETS GUNBONSAI STAT TRACKING MID-SESSION.
      It reads `pawn.player.OffhandWeapon` directly for XP attribution and HUD
      (EventHandler.zsc:220, 289, 339-360; OffhandStatusDisplay.zsc:14-16).

  J8. TRIGGER-GATE STRANDING. `A_RS_ClearTriggerGate` (RS_Weapon.zs:129) reads
      `player.cmd.buttons & BT_ATTACK`. A UI that consumes attack input can
      leave `bWaitingForRelease` true and BLOCK FIRING. Note SMG
      (RS_SMG.zs:167-169) and PlasmaRifle already omit the clear call from
      their Ready states.

  J9. PICKUP CAN CLOBBER A DELIBERATE CHOICE. AttachToOwner:368 overwrites
      OffhandWeapon on ANY offhand-flagged pickup; TryPickup:51-68 Destroy()s
      actors mid-morph; AttachToOwner:387-392 re-tops AmmoType2 to Capacity.

  J10. NO HAPTICS EXIST. Grep for Vibrat/Haptic/Rumble/Feedback across
      zscript/ returns nothing. Grab/hover feedback must be sound + visual
      until the C++ fork.


================================================================================
 PART 4 -- VANILLA+ SELECTOR (the navigation case; the GearBox fight)
================================================================================

SHAPE: the ten Vanilla+ weapons are visually distinct with a classic slot
layout, so the selection problem is "get to the shotgun without thinking."

INTERACTION SKETCH (pick one and prototype; do NOT build all three):
  (a) Proximity grab -- weapon objects float near the hand; nearest-to-palm
      wins on close. No raycast, no cursor, no wedges. Both hands independent
      and simultaneous because nothing is modal.
  (b) Body-anchored positions -- reach to hip/chest/shoulder and pull. Zero
      steady-state visuals; the UI is proprioception. Fastest possible, most
      tuning cost, needs in-headset iteration.
  (c) Controller-ray + wedges -- the conventional port. Cheapest to build,
      weakest differentiation, closest to what the competition already does.

VISUAL ASSET PATH -- ALREADY SOLVED, NO A_ChangeModel NEEDED:
  9 of 10 VP weapons have present, verified .kvx voxels (3E). Only RS_VP_Fist
  lacks one, deliberately. Voxels already spin (DroppedSpin/PlacedSpin 10).
  If A_ChangeModel does work, the five W-*.md3 world models are a nicer subset
  (BFG, Chaingun, Chainsaw, PlasmaRifle, RocketLauncher) but cover only five.

WHAT MUST NOT BE DRAWN: nothing stat-related. VP Condition is always 100.0,
there is nothing to compare, and adding a stat overlay here would import the
main arsenal's problem into the set that doesn't have it.

ENUMERATION HAZARDS FOR THIS SET:
  - `RS_VP_ARifle2` IS COMPLETELY ORPHANED. No code path grants it; grep across
    all .zs/.txt/KEYCONF/MENUDEF finds no reference outside its own definition.
    A naive class-based enumerator will show an unobtainable weapon.
  - `RS_VP_Fist` and `RS_VP_ARifle` are the 2 of 10 that DO NOT override
    `GetOffhandClass()` (RS_VP_Weapon.zs:39-42 returns null), so they can never
    morph to an offhand via TryPickup.
  - SLOT NUMBERS COLLIDE: slot 1 = Fist + Chainsaw, slot 2 = Pistol + ARifle,
    slot 3 = Shotgun + SSG. Slot is not a selection key.
  - SELECTIONORDER TIES: RS_VP_ARifle and RS_VP_RocketLauncher are BOTH 2500
    (RS_VP_ARifle.zs:18, RS_VP_RocketLauncher.zs:17). Values don't correlate
    with slot or power (Plasma 100 lowest, Chaingun 4000 highest).
    SelectionOrder is not a sort key either.
  => The selector needs its OWN explicit ordering. Enumerate by inventory, and
     reconcile with RS_DebugMenu's hardcoded lists (3H).
  - Reverse mapping offhand->mainhand does not exist, BUT every "2" class's
    direct parent IS its mainhand, so `GetParentClass()` is a reliable inverse
    for this set specifically.
  - OFFHAND ACQUISITION IS SILENT: the TryPickup morph fires on a second floor
    pickup with no sound, no message, no event. The player's dual-wield
    inventory changes with nothing to hook.

SWAP TIMING IS UNIFORM AND CHEAP -- all 20 VP classes are exactly
`Deselect: <READY> <frame> 1 A_Lower; Loop;` / `Select: ... A_Raise; Loop;`.
One tic, single frame, no per-weapon variation, no swap sound (Chainsaw's
`Weapon.UpSound` is the only swap-adjacent audio and it comes from the property,
not the state). A selector can assume one fixed symmetric swap cost.
The main arsenal is identical in shape.
