This is a self-contained briefing so a new session can build RS_MonsterMaster
(the monster-side template for RS_Main) without rediscovering anything. It
contains: the decisions already made, the real source data, a census of what
the reference mods actually do, findings from five completed research passes,

than architectural. "Template only, but a hell of a template."


=====================================================================
PART 1 -- PROJECT CONTEXT
=====================================================================

RS_Main (E:\RS_Main) is a VR-focused Doom mod, GZDoom ZScript, engine version
4.14. It is a lightweight looter-shooter layered on Doom's combat. Full design
in docs/rs_00_overview.txt. The parts that matter for monsters:

  * The player manages a small, deeply-developed arsenal across two independent
    hands, not a 30-weapon wheel. Weapons carry rolled stats, a Tier, Condition,
    and grow via GunBonsai. A maxed weapon gets genuinely absurd.
  * MONSTER TIERS ARE THE PRESSURE VALVE. rs_00_overview.txt states monster
    tiers can be adjusted dynamically at runtime, tiering monsters up or down
    to maintain challenge against player weapon power. This is why runtime
    retiering is a hard requirement, not a nice-to-have.
  * Monsters exist Tier 00..14 plus an EX tier. EX ("TEX") monsters are NOT
    ambient spawns -- they are event/SetPiece summon fights, purchased with
    Gold. They do not ride the ambient tier dial.
  * Elite monsters are a SEPARATE axis from tier. Elites drop class weapons;
    normal monsters drop Bits only. A monster should be able to be any tier
    AND independently elite-or-not. Do not conflate these.

The project is singleplayer/VR only. consoleplayer-only reads are intentional
throughout the codebase.

PART 2 -- EXISTING RS_MAIN ARCHITECTURE TO MIRROR AND REUSE
=====================================================================

RS_MonsterMaster is explicitly the monster-side parallel of RS_Weapon. Study
these before designing anything; the monster template should feel like it was
written by the same hand.

zscript/weapons/RS_Weapon.zs
  The model to mirror. Note especially: rolled stats live on the weapon and
  MODULATE whatever attack fires; virtual opt-in hooks (BuildAttackProfiles,
  GetHeavyProjectile, GetFamily, GetBaseKeywords) default to empty rather than
  forcing every subclass to implement them; one dispatch function
  (A_RS_FireSlot) is the single place all attack modes meet.

zscript/systems/RS_AttackProfile.zs
  RS_AttackProfile = one way of attacking (mode, projectile, shot shape, cost,
  sound, feedback actors). RS_AttackSlot = an ordered LIST of profiles plus a
  cursor; firing advances the cursor and wraps. A list of 1 looks like a normal
  weapon; [A,A,B] means "every third shot is B". Mutators (Append / InsertAt /
  Replace / PadTo) are the write targets for runtime upgrades.

  THIS IS THE DIRECT ANSWER TO MONSTER ATTACK "PROFILING." A monster's attack
  rotation is the same data structure. Tier unlocking a new attack = appending
  a profile. Do not invent a second, parallel concept.

  NOTE: RS_AttackProfile's four modes (BULLET/HEAVY/MELEE/HITSCAN) are shaped
  around player weapons. Monsters need more (see Part 6). Decide whether to
  extend RS_AttackProfile or subclass it -- extending is likely cleaner, since
  RS_Weapon ignores fields it doesn't use.

zscript/systems/RS_Catalog.zs
  The audiovisual parts bin -- projectile/sound/effect entries referenced by
  name instead of hardcoded per weapon. Weapons call into it; nothing is
  duplicated across weapon files. Also holds ResolveArchetypeSound() which
  powers the Weapon Sound Assignment menu.

zscript/systems/RS_Keywords.zs
  Shared "key:value" token parser -- StringHas / GetValue / GetValues, plus a
  debug-gated Validate() typo net (rs_debug_validate_keywords). RS_Weapon holds
  the BASE (authored per class via GetBaseKeywords) + GRANTED (runtime, via
  GrantKeyword) storage and query API on top of it.

zscript/systems/RS_KeywordIndex.zs
  Living-draft doc file, not compiled. Documents the weapon keyword taxonomy
  with REAL / RESERVED / CUT annotations per value. The monster keyword index
  should follow this exact format and spirit.

zscript/systems/RS_Roll.zs
  Tier enum + per-tier socket table + Condition banding. The Condition band
  table (GetConditionEffects) is a good model for banded, data-driven
  behavior-shift-by-threshold -- relevant to monster wounded states.

zscript/systems/RS_GunBonsaiBridge.zs
  The only file permitted to reference both RS_ types and vendored TFLV_ types.
  If monsters ever need to touch GunBonsai, that boundary discipline applies.

zscript.txt
  The include manifest. Order is cosmetic (ZScript compiles as one unit) but
  the file is organised by subsystem with explanatory comments. Match the style.

OTHER CONVENTIONS OBSERVED IN THIS CODEBASE
  * Lowercase global min/max, not Min/Max. See RS_Roll.zs.
  * This engine build does NOT reliably resolve
    `static const TYPE name[] = {...}` inside a class body. It has caused three
    separate real bugs. Use comparison chains or switch statements instead.
    If you see "Unknown identifier" on something obviously declared, check this
    first.
  * `extend class PlayerPawn` fails on this build ("cannot be found in current
    translation unit"). Extend VR_DualClassBase instead.
  * Disabled-but-preserved mechanisms use an explicit short-circuit
    (`if (true) return;` / `false &&`) with a comment, not deletion.
  * Comments explain WHY, and honestly flag what is stubbed, placeholder, or
    unverified. Match this. Do not describe a stub as if it were finished.

PART 4 -- DECISIONS ALREADY LOCKED
=====================================================================

D1. NAME: RS_MonsterMaster.

D2. TIERS ARE NUMERIC. RS_T00 .. RS_T14. No colour names anywhere in the enum,
    the API, or the file layout. Colour names were the source of the confusion
    that killed the previous attempt ("is Fireblu above or below Yellow?").
    Numbers are unambiguous, extrapolate cleanly, and let a separate
    colour-environment system own colour independently.

D3. TIER AND COLOUR ARE DECOUPLED. Tier is the only thing balance/combat code
    reads. Colour/tint is presentation, driven later by an environment-glow
    system (wall/floor/ceiling light readings), NOT by a fixed tier->colour
    table. The template must expose colour as an overridable hook, not bake it
    into the tier switch.

D4. GLOW HOOKS ARE STUBS THIS PASS. Wall / floor / ceiling glow probes exist as
    empty virtuals returning 0. We are not ready to build environment-driven
    retiering. Do NOT implement light probing. Do NOT delete the hooks either.

D5. RUNTIME RETIERING IS MANDATORY and must be idempotent -- always recompute
    from cached Default stats, never from current (possibly already-scaled)
    values, so tier-up-then-down cannot drift or compound.

D6. FRACTION-PRESERVING RETIER, TOGGLEABLE. A monster retiered mid-fight keeps
    its health FRACTION rather than being full-healed or left at raw HP. This
    gets an options toggle.

D7. STAGGERED TRANSFORM: KEEP THE CONCEPT, REBUILD THE CODE. See Part 5.

D8. KEYWORD DEATH REACTIONS: KEEP, REBUILD, EXPAND. Route death presentation on
    the KILLING WEAPON'S keywords (dmg:explosive, class:chainsaw, dmg:fire...)
    rather than per-monster hardcoding, so any weapon tagged the same routes the
    same. This is RS_Weapon's keyword system reaching across to drive monster
    behaviour generically. Expand beyond the old set.

D9. OPTIONS MENU BUILT IN TANDEM, NOT AFTER. "Radiant Silvergun Options" ->
    "RS Monster Options", a sibling entry alongside the existing "Weapon Sound
    Assignment". Every dynamic/spectacle behaviour gets a toggle. Rationale:
    default settings keep combat Doom-honest; players who want full chaos crank
    it up. The toggles are the pressure valve that lets us be ambitious without
    wrecking the baseline feel.

D10. EX / TEX MONSTERS IGNORE THE DIAL. A TierLocked()-style virtual returning
    false by default; EX classes override true. They ship hand-authored stats.

D11. CATALOG: BUILD A PARALLEL RS_MonsterCatalog.zs, NOT entries inside
    RS_Catalog.zs. Reasoning: (a) weapon lookups shouldn't wade through monster
    entries; (b) monsters need entry kinds weapons don't have (summon rosters,
    aura FX, gore sets, tier visuals); (c) mirrors the existing subsystem-split
    convention rather than growing one god-file. Everything that CAN be
    catalogued MUST be -- no monster file should name a raw projectile, sound,
    or gore actor inline.

D12. MONSTERS ARE REBUILT AS RS_ ZSCRIPT FILES, ONE PER FAMILY. They do not
     have to be 1:1 ports of CH -- they have to be good. Pull structure and
     intent from CHP's DECORATE, art/sound from ARTSOURCE.

PART 5 -- TIER DATA (THE REAL NUMBERS)
=====================================================================

These 13 rows are CH's actual tuning, ordered by CH's own spawn-rarity weights
(most common = lowest tier). Preserved from HF_Monster.zs's TierData(), which
derived them from CH directly. Row order below is the ENUM order, which is the
authoritative sequence -- note it differs from the order the old switch
statement was written in.

  Tier   hpMul  spdMul  painChance  dmgMul   (CH origin)
  T00     1.0    1.0      200         1.0    Neutral / vanilla baseline
  T01     1.6    1.1      180         1.2    Green
  T02     2.0    1.2      160         1.3    Blue
  T03     1.8    1.6      120         1.3    Cyan
  T04     3.5    1.4      100         1.6    Purple
  T05     3.0    1.7       90         1.8    Yellow
  T06     4.0    1.3      100         1.5    Abyss
  T07     2.5    1.5      110         1.7    FireBlu
  T08     3.0    1.1      140         1.4    Brown
  T09     3.8    1.0       90         1.5    Gray
  T10     5.0    1.5       70         2.0    Red
  T11    12.0    1.6       40         2.5    Black
  T12    20.0    1.8       24         3.0    White

CRITICAL: THIS CURVE IS NOT MONOTONIC AND THAT IS INTENTIONAL. T03 has lower
HP than T02 but much higher speed. T09 is the slowest tier in the whole table
yet nearly the toughest of the mid band. Each row was a distinct hand-designed
creature identity, not a point on a ramp. DO NOT "fix" this into a smooth
curve -- the irregularity is the character of the ladder. A tier is a
personality, not a difficulty number.

EXTRAPOLATED TIERS (new, above CH's ceiling):
  T13    33.0    1.85      16         3.5
  T14    55.0    1.9       12         4.0

  Derivation: the top of CH's own curve escalates by roughly 1.65x per step in
  HP (T11 12.0 -> T12 20.0), with damage climbing +0.5 flat and painChance
  roughly halving. T13/T14 continue that trend. Speed is deliberately capped
  near 1.9 -- pushing monster Speed much past that starts breaking Doom's
  movement/AI rather than making monsters scarier. If T13/T14 need to feel
  worse, they should get it from behaviour unlocks, not raw speed.

  These two rows are ours, not CH's, and are flagged as tuning placeholders.

dmgMul NOTE: hpMul / spdMul / painChance are plain Actor properties the
template can safely rescale in code. dmgMul is NOT trivially applicable --
scaling outgoing damage means reaching into every vanilla attack action
(A_TroopAttack, A_SkelMissile, A_CustomMissile damage args...) across every
monster. Store it as data the monster's own attack code reads and applies.
Do not pretend it is wired when it is not.

TRANSFORM (D7). The old implementation flashed by calling
A_SetTranslation("hfmon_flashwhite" / "hfmon_flashblack") -- translation names
that were never defined in any TRNSLATE lump anywhere. The call silently
no-ops. That is almost certainly why "it never worked in game."
Rebuild using something that does not depend on a named palette lookup.
Keep the two real design intents:
  (a) a small random delay before the tier snaps, so retiering a room full of
      monsters spreads the recompute cost over many tics instead of spiking one
      frame -- this is a load balancer, and it matters;
  (b) a visible tell during that delay, so a mid-fight retier reads as an
      event rather than a bug.

PART 6 -- BEHAVIOUR CENSUS (WHAT CH ACTUALLY DOES)
=====================================================================

Measured across all 17 CH decorate family files, ~5,556 behaviour-function
calls total. This corrects an earlier undercount that claimed ~7 mechanics.

  MECHANIC                              CALLS   FAMILIES
  Summon / spawn other monsters          952     17 of 17
  Persistent per-actor state counters    332     15 of 17
  Mid-fight morph / self-replace         331     17 of 17
  Orbiting / attached satellite actors   247     13 of 17
  Dash / leap / knockback mobility       172     17 of 17
  Homing / seeking projectiles           146     16 of 17
  Aura buff / heal / debuff              92      13 of 17
  Proximity / ally awareness             57      10 of 17
  Health-threshold triggers              54      13 of 17

HEADLINE FINDINGS
  * SUMMONING IS UNIVERSAL. Every single family summons. This is not a boss
    mechanic -- it is a core CH verb. Treat it as a first-class template
    feature with a roster + pack-cap + relative-tier system, not a per-boss
    special case.
  * PER-ACTOR STATE MACHINES ARE PERVASIVE (15/17). CH uses DECORATE user_
    vars as counters: charge-up meters that escalate what gets summoned, one-
    shot enrage guards, timers that expire an orbiting satellite. In ZScript
    these are just plain member fields -- vastly cleaner. The template should
    make "this monster has persistent state that drives escalation" a normal,
    supported thing.
  * ORBITING SATELLITES (247 calls) is a whole category missed earlier: child
    actors attached via A_Warp to a master, circling it, acting as shields,
    damage sources, or visual charge indicators, with their own lifecycle
    tied to the parent. Needs a real attach/detach/cleanup primitive.
  * MORPH IS EVERYWHERE (17/17), not just the Imp/Archvile Pain.AbyssPE case
    found earlier.

NAMED PATTERNS WORTH BUILDING AS SHARED PRIMITIVES
  P1  Summon roster -- pick from a weighted list, cap live pack size, tier the
      summon relative to the summoner, escalate the roster as a charge counter
      climbs. (Gray Archvile summons five other families; the Abyss portal
      ramps Revenants -> Cacodemons as its counter rises.)
  P2  Proximity-adaptive dual behaviour -- allies nearby: heal/buff them;
      alone: switch to an aggressive attack. (Brown Archvile.)
  P3  One-shot threshold enrage -- fires once at a health floor, guarded by a
      flag, permanent for the rest of the fight. (Gray Cybie: quake, speed up,
      aggression flag flip.)
  P4  Timed modifier pulse -- temporary stat spike that auto-reverts, guarded
      against re-trigger while active. In CH this is an ACS delay() coroutine;
      in ZScript it is a stored revert-tic checked in Tick().
  P5  Phase-dodge / blink -- interrupt combat, become briefly untouchable
      (invisible + float + wander, or a multi-directional thrust burst),
      resume. (Cyan Cybie PhaseBack, Abyss Archvile Warp.)
  P6  Range-gated attack branch -- different attack close vs far.
  P7  Attack rotation with a gated finisher -- random pick from a pool, plus
      one extra-dangerous move behind a condition. Maps DIRECTLY onto
      RS_AttackSlot; the finisher is a conditionally-inserted profile.
  P8  Mid-fight class morph -- replace self with a different monster class at
      a pain/health threshold. Single virtual hook.
  P9  Orbiting satellite -- attach child actors to a master, warp them each
      tic, expire them on a timer or on master death.
  P10 Ally-linked lifecycle -- summoner death kills its adds (A_KillChildren),
      or adds dying feed the summoner. Prevents orphaned minions.

DESIGN GUIDANCE ON APPLYING THESE
  The project owner wants these maximised, not minimised -- "dynamic, fun
  tier-interactions would be lively to maximize." The options menu is what
  keeps that safe. Suggested default posture (NOT locked, confirm in session):
  low tiers stay recognisably Doom (stat dial only), spectacle mechanics
  switch on as tier climbs, and every mechanic has a toggle so a player can
  choose pure-vanilla-plus-tiers or full chaos. CommonImp/CommonCybie etc. in
  CH are literally stock vanilla behaviour + an icon, which supports a quiet
  low end. But note this was verified on the Common tier only -- the middle
  of the ladder has NOT been surveyed per-family. Do that before locking a
  posture.

PART 7 -- RESEARCH ALREADY COMPLETED (5 PASSES, DO NOT REDO)

R1. CHP DECORATE\MISC\kw_checks.txt -- DEAD END.
    Despite the name, not a keyword system. 780 near-identical Actor blocks,
    each a one-shot spawn-time redirect: check one of 5 ACS flags, spawn
    variant A or variant B. Identity is encoded in hand-written class names,
    not data. Our existing RS_Keywords key:value approach is strictly better.
    Lesson: do NOT encode monster identity via class-name proliferation.

R2. CHP DECORATE\MISC\icons.txt -- USEFUL PATTERN.
    Floating tier-number icon attached above a monster. Spawned once in Spawn:
    (and again in Raise:) with SXF_SETMASTER, then self-loops warping to the
    master every tic. Cleanup is lifecycle-driven: on monster death the parent
    calls A_GivetoChildren("GoAway",1) and the icon's loop sees it and stops.
    Whole system is gated behind a colourblind/accessibility CVar -- when off
    the actor spawns and immediately stops, so it costs nothing.
    Encodes tier as SHAPE (numeral sprite) and colour as TRANSLATION, so the
    tier is readable without relying on colour vision.
    ADOPT: the SETMASTER + warp + GoAway-on-death lifecycle (this is also
    primitive P9 above, already solved).
    DO NOT ADOPT: CHP pre-drew one sprite per number value (~100+ actor defs).
    Compose two digit sprites (tens + ones, 10 glyphs) instead.
    NOTE: no distance/LOD/monster-count throttling exists -- cost is one
    thinking actor per monster when enabled. Add throttling ourselves.

R3. CHP zscript\customspawners.zsc -- CORE WORTH ADOPTING, SHELL NOT.
    ~570 of 8,418 lines are real architecture; the other ~93% is 17 families x
    225 lines of CVar-name registration boilerplate.
    ADOPT: (a) recursion guard -- reuses bouncecount as a depth counter,
    MAX_RECURSION 32, spawns a visible "Unknown" error marker instead of
    looping silently; (b) two-phase spawn -- BeginPlay chooses the class and
    copies speed/flags, PostBeginPlay does the actual spawn, specifically so
    randomly-spawned MISSILES get correct velocity/source/target; (c)
    sv_nomonsters checked inside the weight loop itself, not as a post-filter;
    (d) two-stage roll -- weighted pick, then a separate 0-255 Probability gate
    on the winner, so an entry can be "selected but still not spawn"; (e) a
    PostSpawn(Actor) virtual hook called after the spawned actor is fully
    initialised.
    DO NOT ADOPT: the CVARRandomSpawnerBase layer that treats DropItem.Amount
    as an index into a 225-entry CVar-name table. Overbuilt for us.

R4. CHP zscript\presets.zsc -- ANTI-PATTERN, CONFIRMS OUR INSTINCT.
    225 CVars (15 tiers x 15 colours, each an independent spawn-weight), driven
    by 62 OptionMenuItem classes (~31 presets x 2 for confirm popups). Each
    preset is a hand-copy-pasted ~280-line block of literal SetInt calls. No
    table, no loop, no shared helper. 9,078 lines total. CHP's own menu.zsc
    opens with the author's comment: "DONT LOOK AT THIS ZSCRIPT, THIS IS AWFUL
    AND I DONT KNOW HOW TO WORK WITH ZSCRIPT ANYWAY!!!"
    THE USEFUL IDEA UNDERNEATH, extracted: players actually want just two
    knobs -- a tier-weight curve (bias spawns weak vs strong) and an
    isolation/exclusion mode (restrict to a subset; CHP's "Difficulty" presets
    are literally just zeroing 210 of 225 cells). Implement as a few CVars
    computed from a formula or a short per-tier array. NOT 225 CVars.

R5. CHP source\Bosses.acs -- DEAD END.
    201KB / 5,101 lines / 724 scripts, and every one is an announcer HUD
    message ("Red Baron is on the fly!"). No health checks, no property sets,
    no spawns, no branching, no functions. Also note: the colour codes in this
    file refer to the PLAYER'S random colour perk, not monster tier.
    Real boss AI/stat/tier logic is NOT here -- it must be in CHP's DECORATE

PART 8 -- WHAT RS_MonsterMaster MUST CONTAIN
=====================================================================

Lean file. Tiers and transforms with hooks. Everything else is a hook, a stub,
or lives in a sibling file.

CORE
  * int Tier, RS_T00..RS_T14 constants. Numeric only. Consider stopping before infering new tiers, a lot is a lot.
  * Cached Default stats captured once, so all scaling is idempotent.
  * SetTier(int, bool instant) -- public entry, safe to call repeatedly at
    runtime, re-targetable mid-transform, no-op when TierLocked().
  * ApplyTier() -- recompute from Defaults. Fraction-preserving health
    (toggleable per D6).
  * virtual TierData(int, out row) -- the per-monster-set tier table hook. The
    base class ships the Part 5 table as the default; a monster set can
    override.
  * virtual TierLocked() -- false by default; EX/TEX overrides true.
  * Staggered transform: random short delay + a visible tell, rebuilt (D7).
  * virtual OnTierApplied(int) / OnRetier(int old, int new) hooks.

VISUAL / ENVIRONMENT
  * virtual GetTintKey() + a settable environment override, so colour is never
    hardwired to tier (D3).
  * Three empty glow-probe stubs: wall / floor / ceiling (D4). Return 0.
    Document clearly that they are deliberate stubs.
  * Tier badge/icon using the R2 lifecycle pattern, toggle-gated, throttled.

KEYWORDS
  * BASE (virtual GetBaseKeywords) + GRANTED (runtime array) + query API,
    mirroring RS_Weapon exactly, reusing RS_Keywords as the shared parser.
  * A sibling RS_MonsterKeywordIndex.zs living-draft doc in the format of
    RS_KeywordIndex.zs. Build a NEW taxonomy from RS_Main's own vocabulary --
    do not inherit CH/HF's species:role:trait:faction set wholesale. Keys
    already sketched: species, set, role, delivery, payload, element,
    mobility, trait. Reuse weapon-side VALUES where the axis is genuinely
