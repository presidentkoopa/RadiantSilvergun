WHY THIS EXISTS

  Three ports have been attempted. All three produced a tree that passed
  every check in the repo and was still wrong. The checks are gone now
  (see CLAUDE.md) because of what they were, not because of their bugs:
  they compared this tree against ITSELF. That cannot tell faithful from
  merely self-consistent, and self-consistent-and-wrong is the exact
  failure that happened three times.

  Owner, verbatim, 2026-08-04:
    "you will import each and every monster in all of its states. do not
     shortcut. each line of attack, appearance, everything. break down
     the ACS byte by byte and rebuild every line in zscript. i don't care
     how much work it is."
    "every monster attack will be cataloged. everything goes into its own
     folder. everything documented. everything cataloged. everything
     described. everything set up to be part of the PACK system."

  That is the specification. It is not negotiable down.

1. GROUND TRUTH
================================================================================

  THE SOURCE IS ON DISK. It is not our tree, not a doc, not a lint.

    E:\New folder\ART SOURCE\CHP\DECORATE\NN\NN_<code>.txt   monsters
    E:\New folder\ART SOURCE\CHP\source\*.acs                behaviour
    E:\New folder\ART SOURCE\CH\decorate\*.txt               fallback
    E:\New folder\ART SOURCE\CH\source\*.acs                 fallback

  CHP ALWAYS WINS. CH fills only what CHP leaves undefined -- CHP is a
  patch on top of CH, so a CHP actor that does not redefine a state
  inherits CH's. Colour code -> tier:
    C=T00 G=T01 B=T02 CY=T03 P=T04 Y=T05 A=T06 F=T07
    BR=T08 GY=T09 R=T10 K=T11 W=T12  KX/WX=TEX and up

  Family numbers:
    01 Zombieman 02 Shotgunner 03 Imp       04 Chaingunner 05 LostSoul
    06 Demon     07 Spectre    08 Revenant  09 Cacodemon   10 PainElem
    11 HellKnight 12 Arachnotron 13 Mancubus 14 Archvile   15 Baron
    16 Mastermind 17 Cyberdemon

  OUR TIER MAPS TO CHP'S `Common<Colour><Family>` ACTOR.

  DECIDED 2026-08-04, so it stops being re-asked: PORT THE `Common*`
  ACTORS. The other sub-variants (Green*, Blue*, Purple*, ... 15 per
  tier, 26,203 actors against the 423 Common ones) are CHP's SPAWN-COLOUR
  axis, and the difference between them is overwhelmingly a `Translation`
  plus scaled Health/Speed/damage. Our tier system already carries a
  TintTable and per-tier stats, so that axis is DATA we can add later
  without re-porting a single state.
  They are NOT dropped and NOT forgotten: each family's README records
  which sub-variants exist and what distinguishes them, with the
  Translation strings copied verbatim, so adding the axis later is a
  table-filling job and not another archaeology dig.
  Sixty times the work for a recolour, before a single tier has been
  confirmed correct on screen, is exactly the trade that produced three
  broad-and-shallow failures.

  NOTHING IS "CRUFT" UNTIL ITS SOURCE HAS BEEN READ. The previous ports
  dropped ACS tokens as "empty wrappers" without opening the script they
  called. The wrapper is empty BECAUSE the behaviour is in the ACS. That
  single mistake removed pack speed buffs, damage resistance auras,
  lead-fire, and the Archvile EX timer.

2. WHAT "PORTED" MEANS -- THE COMPLETION TEST
================================================================================

  A family is DONE when, for every tier it has, ALL of the following are
  true and have been checked against the CHP file with it open:

  [ ] Every state CHP defines exists: Spawn, Idle, See, Melee, Missile
      (and every Missile.* branch), Pain, Death, XDeath, Raise, and any
      named state CHP invents (Scatter, Miss2, Buff, Bomb, ...).
  [ ] Every state's SPRITE TOKEN matches, frame for frame.
  [ ] Every state's TIC COUNT matches.
  [ ] Every action function matches, including its arguments, and every
      damage roll is preserved as a roll (DamageFunction, never a
      constant -- see CLAUDE.md).
  [ ] Every property matches: Health, Speed, PainChance, Scale, Radius,
      Height, Mass, MeleeRange, MeleeDamage, DamageFactor, Translation,
      BloodColor, every sound, Obituary, Tag.
  [ ] Every ACS script the actor calls has been OPENED, read, and
      rebuilt in ZScript -- or explicitly recorded as cosmetic with the
      script body quoted as evidence.
  [ ] Every projectile, puff, gib, summon and effect actor it references
      exists, with ITS states ported to the same standard.
  [ ] Every attack has a catalog entry (section 4) and an
      RS_AttackProfile (section 5).

  ANYTHING NOT PORTED IS RECORDED AT THE SITE WITH THE SOURCE QUOTED.
  Not "cosmetic, dropped". The actual lines, so the next reader can judge
  for themselves. A wrong REASON is more expensive than a missing
  feature: "porting it imports nothing" hid four real mechanics for three
  sessions, while "only the aim-lead math is lost" got fixed the day
  somebody looked, because it described the gap honestly.

3. LAYOUT -- EVERYTHING IN ITS OWN FOLDER
================================================================================

  zscript/monsters/<Family>/
      RS_<Family>.zs              the monster: tiers, states, dispatch
      attacks/
          RS_<Family>_<Attack>.zs one file per distinct attack, holding
                                  its projectile(s) and effect actors
      README.txt                  what this family is, tier by tier

  docs/monsters/<Family>.md       THE CATALOG (section 4)

  RULES
    * One attack, one file. A file may hold the projectile plus the puff,
      trail and explosion that only it uses -- nothing else.
    * Anything shared by two families moves to
      zscript/monsters/_shared/ and is named for what it IS, never for
      the first family that happened to use it.
    * A new file that is not in zscript.txt SILENTLY DOES NOT EXIST.
      Add the include in the same commit that adds the file.

4. THE CATALOG -- EVERY ATTACK, DESCRIBED
================================================================================

  THE CATALOG IS WRITTEN FOR PACK TO READ, NOT FOR A HUMAN TO ADMIRE.
  Owner's framing, and it is the whole design of this section: an entry
  must let something say "Oh, this is a FREEZE RAY. I'll use this for
  ____." So every entry leads with WHAT KIND OF THING IT IS, in the same
  vocabulary the keyword axes already use, and only then describes it.

  docs/monsters/<Family>.md carries one entry per attack. Format:

    ## <AttackName>            zscript/monsters/<Family>/attacks/RS_<Family>_<Attack>.zs
    kind         : freeze ray            <- THE SELECTOR. plain words.
    axes         : delivery:bullet payload:single element:void
                   trigger:semi archetype:hitscan
    tier(s)      : T03 Cyan  (Zombieman)
    chp source   : CHP/DECORATE/01/01_CY.txt:245-268
    acs          : CHSett2.acs "PESPEED" -- rebuilt as RS_PESpeedBuff
                   (or: none)
    fires        : RS_IceZombieShot x1, 42 units up, +-2 degrees
    damage       : random(20,75)          <- the ROLL, never a mean
    sprites      : ICEY ABC (flight) / ICEY FGHI (shatter)
    sounds       : see=ice/Cast  death=Ice/Hit2
    behaviour    : one paragraph, plain words, of what it DOES and what
                   it is like to be hit by
    profile      : RS_AttackProfile.MakeVolley(...) -- the exact call
    notes        : anything CHP does that looks like a bug, quoted

  TWO RULES ON `kind` AND `axes`, because they are what make this useful:
    * `kind` is how a person would name it out loud -- freeze ray, gas
      cloud, bone spear, homing swarm, ground rake. If two attacks share
      a `kind` they should be genuinely interchangeable.
    * `axes` are machine-readable and must use ONLY values that already
      exist in the keyword system. Inventing an adjective here breaks the
      query. If nothing fits, the axis vocabulary gets extended
      deliberately, in rs_17, not quietly here.
      THE LIVE `element:` VALUES ARE: explosive, kinetic, melt, plasma,
      thermal, void. Sweep the tree for the rest before using one --
      `grep -rhoE "axis:[a-z-]+" zscript/` is the authority, not this
      file and not memory.

  A CORRECTION TO THIS SECTION, KEPT AS THE WARNING IT IS: the example
  above used to read `element:ice`. THERE IS NO SUCH VALUE. A cataloguing
  agent caught it, refused to use it, substituted the live `element:void`
  and flagged the discrepancy rather than quietly inventing an axis. That
  is exactly the behaviour this document asks for -- and had it not, this
  spec would have taught all seventeen families to emit a dead value, and
  every PACK query against ice would have returned nothing.
  A SPEC IS NOT EVIDENCE EITHER. Check it against the tree like anything
  else.

  OPEN QUESTION THIS EXPOSED, not to be resolved by guessing: CHP has a
  great deal of ice content -- T03 Cyan is an entire frost tier across
  the whole roster, and its projectiles carry `DamageType "Ice"`. There is
  no `element:` value for it. `void` is the closest live idiom and is what
  the Zombieman catalog uses, under protest. Whether the vocabulary gains
  a cryo/frost value is an rs_17 decision and an owner call; note that
  rs_16 bans ELEMENTAL AFFIX CARDS, which is a different question from
  whether a monster attack may be DESCRIBED as icy.

  A DESCRIPTION THAT COULD DESCRIBE TWO DIFFERENT ATTACKS IS NOT DONE.
  "fires a projectile" is not a description. The catalog exists so an
  attack can be chosen from a list without opening the code.

5. PACK -- EVERY ATTACK IS ASSIGNABLE
================================================================================

  THIS IS THE HALF THE LAST PORT DID NOT BUILD, and the measurement is
  the reason this section exists:

    917  standalone projectile classes  (the parts bin -- real, and good)
    4054 attacks fired INLINE from state code, hardcoded
      30 attacks routed through RS_AttackProfile
       8 of 19 monster files with a tier attack slot

  0.7%. The parts exist; the sockets do not. An attack written as
  `A_SpawnProjectile("RS_X", 32, 0, angle)` inside a state cannot be
  reassigned to anything, which is the entire point of cataloguing it.

  SO: every attack gets an RS_AttackProfile entry, built in
  BuildTierAttacks, and the state fires it through the slot. The
  projectile class stays exactly where it is -- this is about the CALL,
  not the actor.

  The conversion is mechanical: an inline call and a profile entry carry
  the same information (projectile, offset, angle, count, sound). 30
  already work. Nothing needs redesigning.

6. HOW WORK IS DONE AND PROVEN
================================================================================

  ONE FAMILY AT A TIME, COMPLETE, THEN VERIFIED IN GAME BEFORE THE NEXT.

  This is the part that failed three times. Broad-and-shallow passes
  across all 17 families produced a tree that looked finished everywhere
  and was correct nowhere, and no single monster was ever confirmed
  right. Depth-first cannot fail that way: at any moment the count of
  families that are genuinely done is a number the owner has personally
  seen on screen.

    1. Read the family's CHP files, all tiers, before writing anything.
    2. Read every ACS script they call.
    3. Build: monster, attacks, catalog, profiles.
    4. Owner boots and walks every tier with the debug menu.
    5. Punch list -> one fix pass.
    6. Only then, next family.

  THE COMPILER AND THE GAME ARE THE ONLY AUTHORITIES. No script in this
  repo may be treated as evidence of correctness. If a tool is written
  again it must be a DIFFER AGAINST CHP that quotes both sides -- never
  a lint that reads only us.

  NEVER REPORT A FAMILY DONE WITHOUT THE OWNER HAVING SEEN IT.

7. THE WEAPONS QUESTION -- OPEN, NOT ASSUMED
================================================================================

  The owner's concern: "all of this tells me i have to rebuild all of my
  weapons one at a time as well."

  UNKNOWN, AND IT WILL BE MEASURED BEFORE IT IS ANSWERED. The weapons
  came from a different source and a different process than the monsters,
  so the monster port's failure does not automatically transfer. What is
  already known:
    * 32 base weapons, all extending RS_Weapon, all with rolled stats,
      tiers, sockets and attack profiles -- so the PACK half that the
      monsters lack is BUILT on the weapon side.
    * The GH set's profile names branded their source rather than
      describing the attack (fixed 2026-08-04, 21 strings).
    * VR_Fist was outside RS_Weapon entirely until 2026-08-04.
    * The three heavies do not consume ammo -- a known live bug.
  Answering this properly means the same treatment: compare each weapon
  against ITS source, not against our own tree. Not started.
