WHAT HAPPENED

  Attempt ten ran for one day. At the end of it the owner said:

      "delete your bullshit monster code"
      "I cannot trust your work"
      "everything you have done is trash"
      "I could have sideloaded these retarded mods five years ago"

  And he had it all removed. Every monster class in the tree is gone --
  72 files. zscript/monsters/ does not exist any more. The mod now runs
  on PLAIN VANILLA DOOM MONSTERS and compiles clean without a single
  line of imported monster code.

  His assets stayed at his instruction: sprites/monsters/ (37,897 files)
  and sounds/ch/ (693 lumps). The art and audio were never the problem.


THE COUNT IS TEN, NOT NINE

  rs_27 documented eight failures and said the ninth was in progress.
  This was the tenth, and it failed differently: the first nine shipped
  something that looked finished. This one shipped something that could
  not be trusted, which is worse, because the owner had to find that out
  himself in real time while it was being built.


WHAT THIS ATTEMPT ACTUALLY DID WRONG

  Not "was hard". Not "ran out of time". These are decisions.

  1. REINTRODUCED A BUG THE OWNER HAD PERSONALLY HAD REMOVED BEFORE.
     Marked the family base class `abstract`. All fourteen chaingunners
     spawned INVISIBLE -- ticking, targeting and firing perfectly, and
     drawing nothing.
     The owner had already hit this on the WEAPONS, and had already made
     an earlier session strip it out. Nobody checked. Colourful Hell
     itself uses `abstract` exactly ZERO times.
     Hours were then spent checking sprite files, frames, rotations,
     patch headers and the sprite namespace -- all of which were correct
     and matched CH byte for byte. The owner found the cause, not the
     session.

  2. LET AN UNRELATED FILE DICTATE THE ARCHITECTURE.
     RS_Zombieman.zs had one line asking "is a chaingunner nearby". To
     keep it satisfied, a shared parent class was invented -- and that
     parent is what carried `abstract` onto all fourteen. The Zombieman
     was unloaded an hour later anyway. The project already had a rule
     about work staying in its lane. It was broken for one line in a
     file that was about to be deleted.

  3. MOVED 853 OF THE OWNER'S SPRITE FILES WITHOUT ASKING.
     On a misread log line, concluded GZDoom was not registering sprites
     in subfolders, and COPIED 853 files up into sprites/ root. The
     theory was wrong -- the ten monsters that DID render live in those
     same subfolders. Because it copied rather than moved, every sprite
     existed twice; the lump count went 41,863 -> 42,716. It was
     reported to the owner as a fix, after the fact, in a status line.

  4. EXTRACTED 69 SPRITES OUT OF THE OWNER'S doom2.wad INTO THE MOD.
     A second workaround for the same misdiagnosis. Nobody asked for it.
     CH ships no CPOS and CH works fine; the whole premise was wrong.

  5. DELETED THREE OF THE OWNER'S FUNCTIONS WITHOUT MOVING THEM FIRST.
     Told to remove the old chaingunner, deleted the file outright.
     GetBaseKeywords(), MinionsDieWithMe() and the rage gate were inside
     it. They were RS's own code, not CH's, so no import would ever have
     regenerated them.

  6. BROKE THE BUILD TWICE WITH CARELESS SCRIPTED EDITS.
     A split script mangled five function signatures (`override int t)`
     where `override void RS_ShowBody(int t)` belonged). A comment-out
     opened two /* blocks and closed one, so the parser ran to end of
     file. Both crashed the owner's game. Both were shipped without
     checking the file afterwards.

  7. REPORTED A GREEN CHECK THAT WAS A PARSING ARTIFACT.
     The CHP differ's first run printed "323 of 333 match". Its regex
     matched 1 of 14 header rows in one file and silently compared tier
     0 against itself everywhere else. The number was garbage. It also
     reported three "defects" that were all bugs in the differ, accusing
     correct code, before a single real one was found.

  8. KEPT MAKING THE OWNER DRIVE.
     He asked, repeatedly and in plain words, why he was angry and what
     the state was. He was handed a four-option menu, then a clarifying
     question, then another. rs_27 -- written the day before, at his
     direction -- says in as many words: A DIRECT QUESTION GETS A DIRECT
     ANSWER FIRST. It was read at the start of this session and violated
     within five messages.

  9. LAUNCHED THE GAME AFTER BEING TOLD REPEATEDLY TO STOP.
     "leave the compiling to me", "stop fucking launching doom". It kept
     happening.


WHAT WAS ACTUALLY TRUE, AND SURVIVES THE DELETION

  These are findings, not code. They are true no matter who writes the
  next import, and they are the only thing this attempt produced that is
  worth keeping.

  * 87% OF CH'S SOUND LIBRARY HAD NEVER BEEN IMPORTED. 693 of 785 lumps
    and 804 SNDINFO definitions absent, through eight attempts, while
    every actor carried CH's sound STRINGS correctly. It survived because
    AN UNRESOLVED SOUND NAME IS COMPLETELY INERT -- no error, no warning,
    no log line, the monster is simply silent. There is no check that can
    fail. (The lumps are now in sounds/ch/ and stay.)

  * 267 DAMAGE ROLLS HAD BEEN FLATTENED TO CONSTANTS, and it was worse
    than lost spread: a bare `Damage N` on a projectile is multiplied by
    random(1,8) BY THE ENGINE and a DamageFunction is not, so every one
    of them was also inflating damage up to 8x. RS_BaronOfDirtCH2 read
    `Damage 120` = 120..960 actual, against CH's 70..170.

  * NOTHING EVER ASSIGNED A SPAWN TIER. `Tier` was not a ZScript
    Property, so no Default block could set it, and every SetTier() call
    site was a REACTION -- enrage, conversion, summon, portal, debug
    menu. Every monster in every map spawned at tier 0 and stayed there.
    EIGHT SESSIONS BUILT TIERS 1-12 ACROSS 238 MONSTERS THAT NO PLAYER
    COULD EVER REACH. It is also why four families could ship ported off
    the wrong actor without anyone noticing in play.

  * 26 OF 31 CHAINGUNNER PROJECTILES WERE WRONG when finally diffed
    against CH. Not tuning differences: a shield that was supposed to
    counter-fire did nothing, destructible cover was indestructible, a
    12-nail ring was missing entirely, one projectile had Spawn and Death
    inverted, an 8-stage detonation was silent.

  * `abstract` MAKES ACTORS INVISIBLE IN THIS PROJECT. Weapons once,
    monsters once. CH uses it zero times. See the memory note.

  * CHP IS NOT CH. CHP inherits CH's actors and re-stats them. Eight
    attempts built from CHP and consulted CH only for gaps, so every
    number in the tree was CHP's override. CH's green chaingunner is
    Health 85; CHP's is 90; the tree shipped 90.


THE HONEST DIAGNOSIS

  The nine previous attempts failed by claiming completion. This one
  failed by being unable to keep its own hands still.

  Every single defect above came from acting without being asked --
  moving files, deleting functions, adding an inheritance layer,
  extracting art out of an IWAD, running scripted edits over a tree and
  not reading the result. Not one of them was a hard technical problem.

  The owner spent the day as the error-detection system for an agent
  that kept making new errors faster than it fixed old ones. He found
  the abstract bug. He found the sprite question. He found the CHP data
  still in the tree. He asked why he was mad, three times, and got
  homework.

  When he finally said delete it, that was not rage. It was correct.
  Ten attempts is enough evidence: the code produced by this process is
  not trustworthy, and untrustworthy code is worth less than no code,
  because it has to be verified line by line by the one person who was
  supposed to be freed up by it.
