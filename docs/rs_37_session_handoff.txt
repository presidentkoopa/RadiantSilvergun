3. RS_Main: 47 LOAD ERRORS -> ZERO
---------------------------------------------------------------------

The mod would not load at all. Four separate causes, and TWO OF THEM
WOULD HAVE COMPILED CLEAN AND FAILED SILENTLY -- which is the pattern
this whole file exists to warn about:

  * TRNSLATE, the 8 rs_wpn_* tier tints. TWO bugs stacked:
      (a) '%' goes AFTER the '=', not in front
          (palettecontainer.cpp:659-671)
      (b) the channel values are MULTIPLIERS CLAMPED TO 0.0-2.0
          (:542-547), NOT palette bytes. Written as 0-255 all eight
          clamp to 2.0 and every rarity renders IDENTICAL BLOWN-OUT
          WHITE -- compiling clean, with the symptom pointing anywhere
          but the translation table.
    Now the 0-1 ramp, original bytes preserved in comments.

  * TWO CLASSES LEFT AT DEFAULT (DATA) SCOPE -- RS_PanelAssembly and
    RS_DropTriptych. An unscoped Object subclass is data scope and
    cannot call a play function, which was every method they exist to
    call. ~15 errors plus cascading "unknown identifier" noise.

  * fillcolor is `native READONLY color` (actor.zs:120) -- use
    SetShade(). Its own comment says so.

  * THE RS-SET WEAPON CLASSES ARE VR_*, NOT RS_*. The files are
    RS_Revolver.zs etc; every class inside is `class VR_Revolver`.
    THIS ONE IS NOT A COMPILE ERROR -- Spawn() on a missing class
    returns null, the drop never appears, nothing is logged. Five of
    six elite-drop entries were wrong and would have shipped a system
    that worked one time in six. This project has been bitten by the
    same RS_/VR_ confusion before (four dead MODELDEF entries).

ALSO FIXED -- a live gameplay bug, verified independently by
monstertheory and blessed into its file:
  GetDamageCeiling() returns PromotionDamageBaseline * 1.8, but that
  field was written in exactly ONE place: inside Promote(). On an
  unpromoted gun it stays 0, so the ceiling is max(1,0) = 1. Therefore
  Damage Up and Hot Loads are NEVER OFFERED before a first promotion,
  and RS_StateLadderBody()'s ratio pins at >=0.90 so every unpromoted
  gun always fires the Peak body -- the Type1/Hot/Peak ladder never
  steps. Fixed with a guarded CaptureInitialDamageBaseline() after
  RollStats at both roll sites.

CANVAS PAINTING DOES NOT NEED ui SCOPE. `class Canvas : Object native
abstract` with unscoped methods (engine/base.zs:529) and
TexMan.GetCanvas is a plain native static (:332). Marking a painter
`ui` only makes play fields read-only to it. A comment in
RS_EliteDrop.zs still asserts the opposite -- it is wrong.

*** THE POINT IS NOT THOSE TWO. IT IS WHY THEY WERE FOUND. ***

Git stopped and asked in three places, so three places got read.
EVERYTHING GIT AUTO-MERGED WITHOUT A CONFLICT, NOBODY READ AT ALL.
Two branches editing the same functions, and git resolves
non-overlapping edits silently -- if one side removes a line the other
depends on and the edits do not literally collide, there is no marker,
no error, and no symptom except missing behaviour.

WHAT AN AUDIT SHOULD DO, when someone gets to it:
  * diff BOTH parents against the result --
    `git diff 54f3036b^1 54f3036b` and `... ^2 ...` -- anything present
    in a parent and absent from the merge is a candidate loss
  * the pattern to hunt is a REPLACEMENT THAT LOOKS EQUIVALENT: a sound
    instead of a state write, a log line instead of an action, an early
    return instead of a fallthrough, a narrowed type test
  * THE TAKE PATH MATTERS MOST. netevent -> hand resolution -> fist
    reject -> mPayload = null -> flag clear -> AttachToOwner ->
    PendingWeapon -> DropCard(). Any missing step fails silently and
    reads as a dead button.
  * same check on the other merges of 2026-08-06: 2c16d29a, de4640c8,
    208e3f44, and the engine-side merges in E:\UZDXREMA
