Weapon Promotion System

This document captures the Promotion mechanic as worked out in design discussion, building on
docs/rs_00_overview.txt's "Weapon Philosophy" section (the Shining Force 2 promotion idea).
IMPLEMENTED sections describe real code, in RS_Weapon.zs (Promote(), RollPromotionCurse(),
UnlockStat(), GetDamageCeiling(), all called from ApplyUpgradeCard()) unless noted otherwise.
TBD sections are not built yet. This is meant to be revised in place as the system grows -- it is
not a historical record of the conversation, it's the current spec.

--Promotion Gate

IMPLEMENTED: A weapon can only be Promoted while its current Tier is Prototype. No other tier is
eligible. (Exceptions may be added later if a real need shows up -- not designed now.)

--What Happens On Promotion (RS_Weapon.Promote())

IMPLEMENTED, in order:

1. Every rolled stat (DamagePerShot, Accuracy, Velocity, CritChance, Capacity) takes a
   proportional 20% cut from its CURRENT value -- 20% OF the current number, not a fresh re-roll
   into Basic tier's range and not a flat subtraction. An 88 Accuracy becomes 88*0.8 = 70.4, not
   66 and not 68. Applies regardless of a stat's Locked state. Worked example: 42 DAM at
   Prototype, -20%, lands at 34.
2. Tier drops: Prototype -> Basic. GunBonaiSockets is set to RS_Roll.SocketsForTier(Basic) (0),
   read fresh rather than hardcoded so a future tier-table change can't drift out of sync.
3. PelletCount +1, permanent. Flat +1 for every weapon type today. TBD: docs still flags that
   shotgun-family probably wants a different (smaller, per the Cyberdemon-math inference below)
   number here -- not yet decided, not yet built.
4. PromotionCount +1. Never resets, never decreases. Storage only in itself -- see "What
   PromotionCount Drives" below for what actually reads it.
5. RollPromotionCurse() fires (see below).

IMPLEMENTED: Promote() ends with a call into RS_GunBonsaiBridge.OnWeaponPromoted(self)
(zscript/systems/RS_GunBonsaiBridge.zs), which reaches into GunBonsai's own upgrade bag for this
weapon, runs OnDeactivate() on everything in it (so any persistent side effect -- flags, stat
modifiers -- gets properly reversed, not orphaned), then clears the bag. This is the one file
allowed to reference both RS_Weapon and GunBonsai's TFLV_* types directly -- nothing else on
either side should.

GunBonsai Level/XP is deliberately NEVER touched by Promote() -- Level is GunBonsai's axis, not
RS's, and only ever goes up regardless of Tier. A weapon can be Level 8 and Tier Basic at the same
time, immediately after promoting from Level 8 Prototype.

This is repeatable -- a weapon can be built back up from Basic through the tiers again (via
Elite-dropped upgrade cards and further leveling), reach Prototype again, and be Promoted again,
indefinitely. This is the intended loop, not an edge case.

--Promotion Curses (RS_Weapon.RollPromotionCurse())

IMPLEMENTED, mechanism only, numbers/flavor TBD: every Promote() call rolls a
PROMOTION_CURSE_CHANCE (currently a 0.15 placeholder, real odds not decided) chance to
additionally curse one of the five rolled stats, chosen at random. A cursed stat:
  - Takes an ADDITIONAL 50% cut (on top of the universal 20% promotion cut above).
  - Gets Locked (the same LockedDamage/LockedAccuracy/etc flags Cursed-tier weapons set at
    creation -- one shared unlock path for both origins).
  - Grants the weapon a "curse:<statname>" keyword via GrantKeyword.
TBD: the curse's keyword VALUE is currently just the stat name as a placeholder
("curse:damage", "curse:accuracy", etc). Design intent is to roll the actual curse flavor/name
from a real list once one exists ("we will roll from a list later") -- the mechanism (pick a
stat, lock it, tag it) is built and ready for that list to plug into.

--Lifting a Curse (RS_Weapon.UnlockStat())

IMPLEMENTED: removing ANY lock -- whether from Cursed-tier creation or a Promotion curse, same
flags, same function -- doesn't just free the stat, it boosts it 1.5x on top of whatever value it
was sitting at while locked. Guarded so calling UnlockStat on an already-unlocked stat is a no-op
(can't be spammed to stack the 1.5x repeatedly).

--What PromotionCount Actually Drives

1. IMPLEMENTED: GunBonsai's per-weapon XP-to-next-level curve discounts based on PromotionCount --
   15% off per promotion, capped at 60% off, so a promoted weapon (even stuck at Basic, unable to
   hold affixes) re-levels faster than a virgin weapon would. This is the one piece that couldn't
   be a pure `extend class` graft -- GetXPForLevel() is a concrete method TFLV_WeaponInfo calls
   internally, not something extend can override -- so it's a small guarded edit directly in
   zscript/GunBonsai/WeaponInfo.zsc, same precedent as the existing offhand/GBOH additions.
   Placeholder percentages, not final balance.
2. The magnitude of RS's own stat level-up picks (e.g. the "+2 DAM" option) should be bigger at
   higher PromotionCount. NOT YET IMPLEMENTED -- there is no RS-side level-up picker to plug this
   into yet (that UI is GunBonsai's). GetDamageCeiling() (below) is the one piece of this that's
   real code today.
3. Once a promoted weapon climbs back to a socket-bearing tier, the GunBonsai affixes it gets
   offered should come in at a higher rank than a virgin weapon would see at that same tier
   ("level 2 upgrades or something") -- PromotionCount becomes one more input (alongside Family,
   Tier, Keywords) to whatever custom affix-authoring system replaces GunBonsai's stock upgrade
   list. NOT YET IMPLEMENTED. Not designed yet.

--Damage Ceiling (RS_Weapon.GetDamageCeiling())

IMPLEMENTED as a data-only building block; nothing calls it yet. Returns
PromotionDamageBaseline * 1.8, where PromotionDamageBaseline is DamagePerShot as of the most
recent Promote() cut (or the initial roll, pre-promotion). The 1.8x figure is a placeholder taken
from the worked Cyberdemon-math sanity check below, not independently re-tuned. Currently
DamagePerShot only -- per design discussion, DAM-only is fine to start with; extending the same
ceiling concept to Accuracy/Velocity/CritChance/Capacity is explicitly deferred, not decided
against.

Nothing in RS owns a level-up stat picker yet (that's GunBonsai's UI), so this function has no
caller today. It's ready for whichever hook ends up presenting stat choices to read it as a cap.

--Reference Math: How Many Promotions To Fight A Cyberdemon-Scale Boss

Sanity-checked against real numbers pulled from an external Colourful-Hell-style monster tier
reference (HF_Monster/HF_Zombieman/HF_Cyberdemon) -- NOT RS's own monster tiers, which don't
exist yet, but used as a plausible stand-in scale since RS's own monster tiers are expected to
land in a similar range.

Anchors used: fodder-scale HP ~20-110 (Zombieman across its tier ladder), apex-boss-scale HP
~4000-14500 (Cyberdemon across its tier ladder, topping out at the same 14500 for both its two
highest color tiers -- HP scaling plateaus at the very top rather than continuing to multiply
forever, worth carrying into RS's own eventual tier table).

Finding #1: Basic-tier RS_Revolver already rolls DamagePerShot 5-15, which is identical to
vanilla Doom's own pistol/chaingun bullet damage (1d3 x5 = 5-15). A virgin Basic weapon is already
correctly calibrated against vanilla/fodder-scale HP. The low end doesn't need fixing.

Finding #2: chaining the promotion cycle forward from the worked example (cycle 0 grinds a
virgin weapon to 42 DAM/1 pellet at Prototype; each promotion applies the -20% cut / +1 pellet /
then regrows using the ~1.8x ceiling headroom before promoting again) lands at exactly 4 pellets
after 3 promotions -- matching rs_00_overview.txt's own line, word for word: "a three-times-
cashed-in pistol of any tier which fires 4 or more pellets." The math and the original design
note agree independently.

Finding #3: plugging that 3-promotion endpoint (~68 DAM, 4 pellets) into the Revolver's real
RateOfFire (2 shots/sec) gives ~544 DPS one-handed, ~1088 dual-wielded. Against the 14500 HP
apex-boss anchor: ~27 seconds one-handed, ~13 seconds dual-wielded. A real, earned boss fight,
not a curbstomp and not a slog.

Conclusion carried into the numbers above: 3 promotions is the reference threshold for "a
1-pellet-class weapon can now credibly solo an apex-scale boss." This is where the 1.8x ceiling
multiplier placeholder in GetDamageCeiling() came from -- it's the headroom-per-cycle figure that
makes the 3-promotion chain land on 4 pellets. Also implies (per shotgun-class weapons already
starting multi-pellet, unlike a pistol's 1-pellet start) that shotgun-family's promotion pellet
bonus should likely be SMALLER than +1 per promotion, not larger, since they reach "4+ pellets"
without needing the same number of cycles -- still TBD, but no longer a blind guess.

--Curse Bits / Repair (Grey) Bits (zscript/systems/RS_Bits.zs)

IMPLEMENTED: two new stacking currency pickups, same pattern as ammo (accumulate in inventory,
no auto-effect) rather than the instant-effect Health/Armor/Ammo bits. Both reuse the Health
Bit's gem sprite recolored via STYLE_Shaded + SetShade instead of new art -- RS_Bit_Grey
(silvery grey, repair/Condition currency, joins the normal weighted kill-reward pool via
rs_bits_ratio_grey) and RS_Bit_Curse (rust red, deliberately rarer and OUTSIDE the weighted
pool -- its own independent per-kill roll, rs_bits_curse_chance, default 5%).

NOT YET IMPLEMENTED: actually spending either currency. RS_Weapon.RepairWithGreyBits() and
UnlockStat() both already exist and do the real work once called -- what's missing is the menu
action that lets the player choose a weapon, choose a curse (or confirm a repair), and spend.

--Curses: STUBBED OFF

The whole curse mechanism (RollPromotionCurse on the weapon side, the Curse Bit kill-reward roll
on the bits side) is short-circuited off for now -- same disable idiom as RS_Roll's earlier
Condition-effects stub. Everything below in this section describes the built mechanism as it
exists in code, not what's currently active. Flip it back on later; nothing was ripped out.

--Curse Roll Frequency (RS_Weapon.RollPromotionCurse())

REVISED, IMPLEMENTED: not a flat chance forever. Escalates with PromotionCount -- your 1st
promotion gets 1 independent PROMOTION_CURSE_CHANCE roll, 2nd promotion gets 2 rolls, 3rd gets 3,
etc. Each roll can land on any of the five stats independently (no dedupe against a stat already
hit in the same Promote() call -- kept deliberately simple).

--What's Implemented vs Still Open

DONE: promotion gate/cut/pellet/sockets math, curse mechanism + escalating frequency, unlock's
1.5x payoff, damage ceiling stub, GunBonsai affix-strip graft, GunBonsai XP-curve discount graft,
Curse/Grey Bit pickups + kill-reward wiring.

STILL OPEN:
- Actually spending Curse Bits / Grey Bits -- the menu/UI action. Nothing calls
  UnlockStat()/RepairWithGreyBits() yet outside of what Promote() itself triggers.
- Bigger stat-level-up magnitude from PromotionCount, and affix rank from PromotionCount --
  both need an RS-side (or grafted) level-up picker to exist first; there isn't one yet.
- Shotgun-family's per-promotion pellet bonus (see Finding #3 above -- probably smaller than +1,
  exact number not set).
- Whether GunBonsai abilities gained by a promoted weapon grant some small permanent secondary
  bonus (e.g. +0.3% crit chance) on top of everything else. Explicitly tentative -- may not
  happen at all.
- PROMOTION_CURSE_CHANCE's real per-roll value (currently a 0.15 placeholder) and the real curse
  flavor/name list RollPromotionCurse's keyword value should eventually roll from.
- Whether GetDamageCeiling()'s mechanism extends to stats beyond DamagePerShot.
- Making Prototype tier rare (drop-rate/roll-odds tuning pass, not a mechanic -- can also be
  addressed by gating how often Elite drops offer higher-tier upgrade cards at all -- deferred).
- RS's own real Monster Tier System numbers (rs_00_overview.txt's Tier 00-14 + EX Boss) -- the
  Cyberdemon/Zombieman math above is a stand-in, not RS's actual data. Once real numbers exist,
  the "3 promotions to boss-viable" conclusion should be re-checked against them, not assumed.
- The custom GunBonsai HUD/menu screens (Tier/Condition/PromotionCount/curse display, curse
  removal, weapon-status toggle screen) -- planned, not started. Drawing primitives confirmed
  available (colored DrawText, Screen.Dim/tinted-texture for bars/panels, DrawLine for borders).
