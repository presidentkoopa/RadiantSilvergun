--------------------------------------------------------------------------------
WHERE WE ARE / WHY THIS FILE EXISTS
--------------------------------------------------------------------------------

Started as: audit the 11 main-arsenal weapons for conformance to RS_Weapon /
RS_AttackProfile. That audit passed -- all 11 build attack profiles correctly.

It expanded (correctly, not scope creep for no reason) once we found:
  1. GunBonsai doesn't read our systems at all -- it's fully generic, works
     via runtime heuristics and its own affix classes.
  2. GunBonsai's affixes are getting deleted and replaced with our own,
     hooked into RS_AttackProfile / RS_Roll directly.
  3. That replacement needs SOME way to classify weapons that isn't runtime
     guessing -- hence keywords.
  4. Keywords needed real evidence, so we read the GH_ weapon set too
     (visually broken/mis-ported, but behaviorally real code, valid for
     this purpose).

This file is the output of all of that. Read this instead of re-deriving it.


--------------------------------------------------------------------------------
THE TWO RULES (unchanged from the original schema attempt)
--------------------------------------------------------------------------------

RULE 1 -- A keyword is a permanent fact about a weapon CLASS, not an instance.
  Tier, DamagePerShot, Accuracy, Velocity, CritChance, Capacity, Condition,
  XP, Level, PelletCount -- these are already real fields on RS_Weapon.
  Not keywords. Don't re-tag them.

RULE 2 -- If a tag reads the same on every weapon, it's decoration, cut it.
  This rule caught real mistakes during this session (see FEED below) --
  trust it over instinct.


--------------------------------------------------------------------------------
KEYWORD SCHEMA v1 -- every axis below is backed by an actual code split
found across the 11 main weapons + the GH_ set, not invented.
--------------------------------------------------------------------------------

archetype:   revolver  pistol  smg  rifle  shotgun  supershotgun  chaingun
             flamethrower  railgun  launcher  energy  bfg  melee

    Closed set. GH Minigun collapses into "chaingun" (mechanically
    identical to VR_Chaingun -- full-auto, belt-fed, hitscan-ish). GH
    Assault Shotgun stays "shotgun" -- trigger:full-auto is what makes it
    different, not a new archetype.

trigger:     semi-auto   full-auto

    Only two real values exist in the code. RS_Weapon has exactly two
    firing gates: CanFireSemiAuto() and AutoCooldownReady(). Nothing else
    is built.
    IMPORTANT CORRECTION FROM THIS SESSION: GH Minigun does NOT spin up.
    GH Railgun does NOT charge. Both are just plain full-auto / semi-auto
    respectively -- the names promise mechanics the code doesn't have.
    charged / wind-up / spooling / burst-3 are NOT reserved-but-real, they
    are UNBUILT. Adding them means new engineering in RS_Weapon /
    RS_AttackProfile (a windup timer, a charge meter), not just a tag.

delivery:    hitscan   projectile   heavy   melee

    Not a new concept -- this is literally RS_AttackProfile.Mode
    (RS_ATK_HITSCAN / RS_ATK_BULLET / RS_ATK_HEAVY / RS_ATK_MELEE) already
    in the code. The keyword just names existing data.

payload:     single   multi

    Category of "how many projectiles leave the barrel on ONE trigger
    pull", not ammo consumption. single = 1 (revolver, pistol, most of the
    roster). multi = shotgun family (7/20/14 pellets) where Choke becomes
    a meaningful stat. GH Assault Shotgun is multi AND full-auto --
    those two axes are independent of each other.

feed:        atomic-fill   incremental   pool   none

    CORRECTED DURING THIS SESSION -- originally drafted as six values
    (speedloader/magazine/break-action/belt/cell-direct/none), but per
    Rule 2 that was wrong. Checked the actual reload code:
      - Revolver, Pistol, Rifle, SMG, SSG, GH Assault Shotgun, GH Railgun
        ALL call the exact same function, A_RS_ReloadAtomic(), fill to
        Capacity in one call. Only the animation wrapped around it
        differs -- that's flavor, not mechanism. All collapse to
        "atomic-fill".
      - Shotgun alone uses A_RS_ReloadIncremental() in a loop, one shell
        per pass, interruptible. Genuinely different mechanism:
        "incremental".
      - Chaingun + all heavy ordnance (Rocket/Plasma/BFG) + GH
        Flamethrower/Minigun/Unmaker/BFG10k draw straight from reserve,
        no chamber at all: "pool".
      - Melee: "none".
    SSG alt-fire (single barrel) is NOT built yet (comment in the file
    says so explicitly) -- nothing to tag there until it exists.

element:     kinetic   explosive   plasma

    Base damage flavor. GH Grenade correctly sets DamageType "Explosive".
    KNOWN BUG, flagged not endorsed: GH Flamethrower's attack profile is
    MakeBullet() pointed at PROJ_Ballistic() -- the SAME catalog entry a
    pistol uses. No fire damage type, no burn effect, nothing thermal
    despite the name/sprite. element:kinetic on a "Flamethrower" is the
    keyword system correctly exposing a bug, not describing intended
    behavior.

set:         radiantsilvergun   gunstarheroes

    Literal weapon-set origin. Practically useful right now because the
    GH_ set is confirmed visually/asset-broken from a bad port -- this tag
    doubles as the worklist for remediation.


--------------------------------------------------------------------------------
KNOWN GAPS / BUGS FOUND DURING THE AUDIT (not fixed yet, just recorded)
--------------------------------------------------------------------------------

1. Rocket/Plasma/BFG (both sets): DamagePerShot is rolled but NEVER
   applied -- comments in the files say "tracked, not yet applied."
   Damage is still vanilla Rocket/PlasmaBall/BFGBall's built-in fixed
   value. Tier does nothing for these weapons yet.

2. Same three weapon families: ammoCost is deliberately 0 in their
   AttackProfile. Known "infinite ammo on heavy weapons" issue, carried
   forward on purpose during the refactor, not accidentally reintroduced.

3. Main-11 weapons reference raw sound names directly ("9mmshoot",
   "m16shoot", etc.) instead of going through RS_Catalog. The GH_ set
   does this correctly (RS_Catalog.SND_GH_*()) -- GH is the better
   example here, main-11 predates the catalog.

4. RS_Catalog's PROJECTILE side is thin/inconsistent: only 3 entries
   exist (PROJ_Ballistic, PROJ_BallisticType1, PROJ_GrenadeLaunched).
   [Historical note, since superseded -- the catalog has grown well
   past this, and the tracer visual mentioned in earlier drafts of this
   doc has been removed entirely, cvar and all, per later direction.]
   Every heavy weapon in both sets names "RS_EnhancedRocket" /
   "RS_EnhancedPlasmaBall" / "RS_EnhancedBFGBall" as a raw string
   literal instead of a catalog call. Same non-conformance pattern as #3,
   other axis.

5. Chaingun (both sets) and Chainsaw (GH_ specifically): no projectile
   actor is spawned (hitscan/melee), so nothing carries the `master`
   pointer GunBonsai reads for XP attribution. Pre-existing, documented
   in the code itself, not introduced by anything we did.

6. GH Flamethrower: see "element" above. Mechanically a fast pistol, not
   a flamethrower.

7. Chainsaw trigger mismatch: VR_Chainsaw (main) is full-auto-gated,
   RS_GH_Chainsaw is semi-auto-gated. Same archetype, opposite trigger
   feel. Not necessarily a bug -- could be intentional variety -- but
   worth a deliberate decision rather than leaving it as an accident of
   two different ports.


--------------------------------------------------------------------------------
GUNBONSAI -- WHAT WE CONFIRMED
--------------------------------------------------------------------------------

- GunBonsai (TFLV_ namespace) is fully generic and does NOT read
  RS_Weapon / RS_AttackProfile / RS_Catalog at all today.
- It classifies weapons via runtime heuristics (counts hitscans vs
  projectiles vs melee as they actually happen -- WeaponTypeInference.zsc)
  rather than reading any authored data.
- Its affix hook interface (TFLV_Upgrade_BaseUpgrade: OnActivate,
  OnProjectileCreated, ModifyDamageDealt, OnDamageDealt, OnKill, etc.) is
  real, generic, and WORKS TODAY -- can be called with our own logic
  inside it. This is the piece worth keeping.
- Its ~15+ stock affixes (BouncyShots, FastShots, PiercingShots,
  WeaponDamage, the elemental trees, etc.) are the part getting deleted
  and replaced with affixes that call AppendProfile/ReplaceProfile/
  InsertProfileAt on RS_AttackSlot, or write RS_Weapon's rolled stats /
  trigger Promotion.
- TFLV_Upgrade_Dot (Fire.zsc/Poison.zsc/Acid.zsc/Lightning.zsc's shared
  base) is GENERIC INFRASTRUCTURE, not affix content -- a stacking DoT
  item with softcap math, independent of GunBonsai-specific logic except
  one priority field. OPEN DECISION: keep this as the DoT engine for our
  own element:thermal/corrosive/shock affixes, or build a fresh one.
  NOT DECIDED YET.
